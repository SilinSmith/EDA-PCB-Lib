# 第二 / 第三阶段：文字识别、角色分配、LLM 仲裁

> 任务是「把原理图 PNG 还原成 `{components, pins, nets}` 的结构化 JSON」。
> 第一阶段（`..\stage1\`）给出**几何**：元件框、引脚点、导线图、网络。
> 本目录（`stage2`）给出**文字**：把每个文字框读出来，判它属于哪个元件的哪个字段。
> `stage3` 只做一件事：把 `stage2` 拿不准的位号做成**选择题**交给 LLM（本机没有
> LLM 环境时用本地 stub，见 §5）。

## 3. 输入 / 输出 schema

**输入**：`<stage1>\<case>.stage1.json`
- `components[]`：`{id, type, bbox_img, bbox_json, center_img, key, ...}` —— 注意 **stage1 的 `key` 全是 `None`**，位号只能靠这里读出来。
- `texts[]`：`{id, bbox_img}`（图像坐标，左上原点）
- `pins`：`{cid: [[x,y], ...]}`；`nets[]`：`{id, pins, n_seg, seg_index}`；`image`：`{path, w, h}`

**输出**：`<out>\<case>.json` = `{"case", "components", "pins", "nets"}`
- `components` 的**键就是位号**（读不出位号时用占位 `p000`）—— 官方按 key 匹配元件，所以一个字符错整条链（它的 pins 与它挂的网络）一起丢。
- `pins` 的键是引脚号，`pinname` 是引脚名；**官方 `pin_f1` 要求 `pinname` 字符串严格相等**。

## 4. 实测（这些数字是设计依据，不是估计）

### 4.1 文字框是瓶颈，不是 CRNN
`work\_ocr_boxcmp.py` 在 10 张 CVJsonStd 上对照（真值 = `texts[].location` + `content`）：

| 臂 | exact |
|---|---|
| 直接用**真值紧框**喂 CRNN | **0.4127** |
| 用 `cvparts.textbox` 的**检出框** | 0.0266 |

⇒ 同样的 CRNN，换个框差 **15 倍**。`work\_boxquality.py` 说明为什么：检出框对真值框的
**最好单框 IoU 中位只有 0.357**（`>=0.5` 只占 11.5%）、**19.7% 的检出框落在所有真值框之外**
（是电阻锯齿、三极管、电池这类**图形符号**被当成了文字），4.2% 的真值框完全没被检出。
`cvparts.textbox` 当初是为「引脚名**覆盖**率 @20px 0.9864」调的，不是为「精确裁字给 OCR」调的。

**修法（已落地）**：`text.py` 的 `pad_box` 在裁给 CRNN 之前四边各外扩 `max(2, 0.30*字高)`。
`work\_ocr_pad.py` 的臂扫描（1248 个框）：

| 臂 | exact | | 臂 | exact |
|---|---|---|---|---|
| 不外扩 | 0.0809 | | prop 0.30h | 0.3870 |
| fix 2px | 0.3790 | | prop 0.45h | 0.3822 |
| fix 3px | 0.3846 | | grow 到墨迹边界 | 0.0753 |
| fix 6px | 0.1194 | | **max(2, 0.30h)** | **0.3918** |
| fix 8px | 0.0465 | | 参照：真值紧框 | 0.4127 |

外扩**只改裁给 CRNN 的那块图**，`reads[i]["bbox"]` 仍是原框 ⇒ `assign` 的几何归属不受影响。
「生长到墨迹边界」完全没用（会顺着符号和邻居长出去）。

**副作用（真实分数）**：5 张官图上的位号赋值率 **0.063 → 0.387**。

### 4.2 CRNN（`..\textrec\`，在 CVJsonStd 真实语料上从零训）
语料 = `Dataset300` 的 32 个 `*_CVJsonStd.json` 里 6684 条 `texts`，只保留 5 个计分角色
（designator / value / pin_name / pin_number / net_label）⇒ 3829 条，字符表 71 字 + blank。
**val 按整张图隔离**（7 张：0059/0112/0123/0146/0171/0182/0254），不会同图泄漏。

epoch 71（`valCER 0.1989 / valExact 0.6433`）：

| 角色 | exact | CER | n |
|---|---|---|---|
| pin_number | **0.760** | 0.211 | 271 |
| designator | 0.735 | 0.106 | 113 |
| pin_name | 0.618 | 0.226 | 199 |
| net_label | 0.546 | 0.194 | 110 |
| value | 0.359 | 0.213 | 92 |

**置信度不能用来过滤误检**（`work\_ocr_conf.py`，2109 正 / 364 负）：正样本 conf 中位 **0.435**、
负样本中位 **0.610** —— 符号的置信度**反而更高**，任何 conf 门槛都先杀真文字。
也**不能**用 conf 兜错：`C1 → C` 的 conf 是 0.99（高置信度丢字）。

### 4.3 位号的前缀矫正：对，但要选 strict
位号首字母由类型决定（`r` 一定是 `R`），所以「尾部数字对、首字母错」的读法可以救回来。
`work\_des_ceiling.py`（20 张 / 258 个有位号的 GT 元件）：

| | 数 | 比例 |
|---|---|---|
| ① 识别天花板（全图任一框读出正确位号） | 129 | 0.500 |
| ② 读得出的里面，**最近的框**正好是它 | 71/129 | **0.550** |
| ③ ①∧②（「就近取框」的实际上限） | 71 | 0.275 |
| ④ **前缀矫正后**读得出 | 187 | **0.725** |
| ⑤ ④∧② | 76 | 0.295 |

⇒ 两个**等量级**的损失：识别（0.50 → 0.725 可救）与**归属**（读得出的里面只有一半
落在最近的框上，因为图形符号常被检出而且**正好压在元件中心**）。

`assign.PREFIX_MODE` 三臂实测（5 张官图，逐张权重得分**求和**）：

| 模式 | 做法 | 位号赋值率 | 5 张得分和 |
|---|---|---|---|
| `off` | 不矫正 | 0.379 | 20.00 |
| **`strict`（默认）** | 只信「字母已在该类型的预期前缀集合里」的读法 | **0.264** | **26.67** |
| `force` | 字母不在集合里也强行换成首选前缀 | 0.353 | 24.86 |

⇒ **赋值率不等于正确率**：`strict` 键更少但更准，得分最高。`force` 会把引脚名
（`P_31`）强行变成 `U31` —— **凭空造键比漏键更伤**。

**全局一对一匹配（`_global_match`，匈牙利）实测净亏，默认关闭**：位号赋值率
0.387 → 0.320、5 张得分和 26.30 → 24.86。根因是前缀矫正会制造一批弱候选，全局匹配
把它们也纳进来。函数保留在代码里可 A/B（`assign(..., global_match=True)`）。

### 4.4 第三阶段：只做选择题
`stage3` 把 `stage2` 每个元件的**全部位号候选**（`desig_slots`，最多 6 个）装成
`cvparts.hypo.CaseHypotheses` 的槽位，`auto_resolve()` 先把只有一个候选的按
`rule:unanimous` 定掉，剩下的真歧义交给仲裁：

- `--mode llm`：走 `stage1.llm.arbitrate`（线程池 + 只接受落在候选集合里的答案）。系统提示词强制只输出 `{"choice": <候选原样>, "confidence": 0-1, "why": "一句话"}`，全不对输出 `null`。**不让模型自由生成** —— 官方按 key 匹配，编一个值就是多一个错元件。
- `--mode stub`（本机默认，因为没有 `LLM_BASE_URL`/`LLM_MODEL`）：**全局唯一性** —— 同一张图里位号唯一，撞号的低分者让位给次优候选。这治的正是 `stage2` 逐元件独立取最优时必然出现的撞号。
- 仲裁结果**回填 `assigned` 后重新 `build_doc`**，不是改字符串：改名牵动 `pins` 的键和 `nets[*].hyperGraph` 里的 `(位号.引脚号)`。

5 张官图：stage2 平均 **5.3324** → stage3(stub) **5.6118**。

## 5. 已知限制（诚实清单）

1. **端到端分数还很低（220 张平均 7.06 / 100）**。`component` F1 只有 0.085、`pin` 0.007、`net_line` 0.006。器件失配里 `missing 7494 / extra 7444` 几乎对半 —— **位号这一个字段挡住了 0.30 分，也顺带堵死了另外 0.70**（官方按 key 匹配元件，键不对，它的 pins 和挂在它身上的 nets 一起丢）。
2. **文字框切分没重做**。目前只做了外扩（把可用性从 0.027 救到 0.392）。`cvparts.textbox` 本来是为覆盖率调的，19.7% 的检出是图形符号。正确做法是在 stage1 已有的导线掩膜基础上，从墨迹重做「字符连通域 → 按行分组」的紧框切分，这是当前最大的一条杠杆。
3. **归属那一半还没治**（0.55）。符号误检压在元件中心，`assign` 的「就近取框」会被它抢走。
4. **`pin_f1` 的结构性门槛**：官方键是 `(component, pin_number)` 且 `pinname` 必须字符串严格相等 ⇒ 引脚号/引脚名只能靠 OCR，几何位置再准也拿不到这 0.25。
5. **`cvparts.textbox` 的 pin-name 覆盖率自检只在 5 张上跑过**，不是 220 张。
6. **本机没有 LLM 环境**，所以 `--mode llm` 这条路没被真实端点验证过，demo 走的是 stub。
7. `stage2_eval` 的汇总行曾经是坏的（读 `summary.get("score")` 而 `aggregate()` 返回的是 `mean_score`；`summary.get("component")` 这个键根本不存在，所以 tp/fp/fn 打印全 0）—— 已修，别改回去。
8. `cv2.imread` **读不了非 ASCII 路径**（`Dataset300我不知道干嘛用的先放置`），一律用 `imread_unicode`（`cv2.imdecode(np.fromfile(...))`）。

### 教训：每个评测/工具函数都要带合成自检
本项目已经在「没有自检的评测函数」上栽过四次：网格索引静默漏找最近段（连通 R 低报 6 倍）、
`argmin` 在长度 1 的数组上恒为 0（整个消融表的连通列报废）、`dist_pts_to_segs` 返回 `(M,)`
而不是 `(M,N)`、`np.concatenate(axis=0)` 让每段与自己的序号后继并起来（整张图塌成一个分量）。
`assign.py` / `assemble.py` / `stage1\pins.py` / `stage1\nets.py` / `stage3` 全部带自检，改动后必须跑。

## 文字框来源与「重切」的端到端结论（220 张实测）

`stage2.run` 现在有 `--texts` 开关，三档可选（默认 `stage1`）：

| `--texts` | 框从哪来 | 官方权重得分 | component F1 | text_mismatch |
|---|---|---|---|---|
| `stage1`（**默认**） | stage1 产物 `texts`（旧 `cvparts.textbox`） | **6.7307** | 0.0846 | 1028 |
| `union` | 旧框保底、新框收紧 | 6.6592 | **0.0855** | **1021** |
| `detect` | 当场跑新 `cvparts.textseg` | 6.4480 | 0.0765 | 1145 |

外扩上限（`STAGE2_PAD_MAX`，**默认已改为 99.0 = 不设上限，即纯按高度 0.3h**）：**对旧 `textbox` 的偏小框，按高度 0.3h 外扩明显更好**（`=99` 得 6.7307，`=3` 只有 6.4878）。⚠️ 曾经的默认值 `3.0` 是个**错的默认**——它比 `0.3h` 低 0.24 分，是在 `textseg` 的「紧框」上扫出来的最优值，被误用到了 `textbox` 的框上。

**要点**：`cvparts.textseg` 在「已匹配的框」上把 OCR exact 从 0.3974 拉到 **0.6496**，但**端到端分数反而更低**——它把「连通分量里带长直线」的整块当结构分量丢掉，**少切约 8% 的文字框**（10 张上命中 1152/1287 vs 旧 1248/1287）。丢一个位号 = 该元件 key 对不上 = **同时吃一个 fp 和一个 fn**，代价远大于「框紧一点、字认准一点」的收益。所以：

- 想要召回 → `--texts stage1`（默认）
- 想要更准的器件名/参数 → `--texts union`
- `detect` 只在没有 stage1 产物时才自动兜底

`stage2\text.py` 的 `merge_boxes(base, det, min_iou=0.25, max_grow=1.25)` 是 `union` 的实现：以旧框为准，能在新框里找到「IoU>=0.25 或中心互相包含」且面积不超过 1.25 倍的对应框就换成新框，找不到就原样保留旧框。

## 「期望」与「结构化批量重绑定」（用户 m06470 的两条指令）

**动机**：`work\reports\错例集_导线与元件.md` 里 **7645 条 `component.text_mismatch` 是最大的一项**——`0001` 四个 IC 的 `Name` 全错（`RP2350B`→`GP/2`、`RM2`→`P1C1`、`APS6404L-3SQR-ZR`→`C1H+`、`W25Q128JVPM`→`1.0KF`），全是**长器件名被切碎**。

### `expect.py` —— 「期望」
由**前缀**推这个名字该有多长，再挑框：

| 前缀 | 期望 | 例子 |
|---|---|---|
| `LONG_HINT`（`STC`/`STM`/`RP`/`ESP`/`W25Q`/`APS`/`MSP`/`NRF`/`TPS`/`MAX`…） | `(len(lead)+3, 32, "partname")` —— **出来就知道名字不可能短** | `RP2350B`、`STM32F103` |
| `REF1` 单字母（`R`/`C`/`L`/`D`/`Q`…） | `(2, 6, "designator")` | `R5`、`C10` |
| `REFN` 已知双三字母（`SW`/`TP`/`LED`/`CN`/`JP`…） | `(2, 6, "designator")` | `SW1`、`TP3` |
| 其它 >=2 字母 | `(5, 32, "partname")` | `RM2`（会偏短，见下） |

`fragment_score(text)` 判「像不像被切下来的一块」：`len<=5` +0.45、`len<=2` +0.2、无小写 +0.15、含 `/-._+` +0.15、全数字 +0.15、**>=2 前导字母且有数字且无分隔符 −0.25**。
`merge_runs(boxes, texts, char_h, gap_mult=1.6)` 把同一行相邻碎片拼长，**只在拼出来 `expect` 判为 `partname` 时才产出**（这条挡掉 `R1`+`R2` 这种误拼）。

### `structmatch.py` —— 结构化批量重绑定
把「谁离引脚最近就归谁」换成**整排一起解**：

1. `group_by_edge` —— 引脚按自己所在边分组；候选归到**离它最近的那个引脚所在的边**（按到 bbox 四条边的距离判会把角落外侧的框判错边，于是永远配不上）。
2. `align_monotone(w, cover)` —— O(n·m) DP，**匹配不许交叉、两侧都能悬空**，`cover` 是每配上一对的固定加分。它就是让「1悬空,1-2,2-3,3-4,4悬空」这种自洽整排压过「只配最近那几对」的旋钮。
3. **数值离群剔除** —— 引脚号 `1,2,3,4` 天然单调，所以对已配上的值跑 `monotone_keep`（最大权严格单调子序列），不在其中的候选**整行硬清零**。硬清零是必须的：最大权 DP 里「配一个正收益的坏候选」永远比「让引脚悬空」划算。
4. `_ladder` —— 数值严格单调且个数等于引脚数时，把第 k 小的值绑到位置上第 k 个引脚，作为整体方案与位置对齐方案**比分取高者**。
5. 两种方案对同一引脚给出不同候选时写进 `ambiguous`，经 `assign` 输出为 **`struct_slots`** —— **这就是留给第三阶段 LLM 的接口**。

### 220 张实测（同一 `stage1_all14`、同一评测器）

| 配置 | 得分 | component F1 | pin F1 | netHF1 |
|---|---|---|---|---|
| 旧 assign + `PAD_MAX=3` | 6.4878 | 0.0813 | — | — |

| 新 assign + `PAD_MAX=99` + `--recut expect` | 6.7899 | 0.0849 | 0.0078 | 0.1138 |

**三条必须如实说的话**：

1. **`structmatch` 有真实收益**：pin F1 `0.0069 → 0.0078`（tp `161 → 183`，+22）、netHF1 `0.1133 → 0.1138`、总分 `+0.045`。component 一行**完全没动**。
2. **`fit_partname` 的重写（期望机制）在官方指标上没换来东西**：`text_mismatch` 1028 → 1029，component F1 0.0849 → 0.0849。原因是 `fragment_score` 区分不了 `RM2`（真名字）和 `P1C1`（碎片）——两者都是「<=5 字符、无小写、>=2 字母带数字无分隔符」，拿到同样的 0.35。**期望要起作用，得先知道框里到底有几个字**，而那是切分的问题，不是打分的问题。
3. **`--recut expect` 是个净零的空转**（6.7912 → 6.7899，四项指标逐项相同），却要多花 8 s。默认 `off`。

**顺带查出的一个错默认**：`text.py` 的 `PAD_MAX` 默认原本是 `3.0`，那是当初在 **`textseg` 紧框**上扫出的最优值，被误用到了 **`textbox` 的偏小框**上，白丢 **0.30 分**。已改为 `99.0`（= 纯 0.3h）。

## 一个静默吃分的 bug：`pins` 的索引键在 JSON 往返后变成字符串

`assemble.py` 里是 `pinfo.get(k)`，`k` 来自 `enumerate` 是 **int**。

- 阶段二内部调用 `build_doc` 时 `assigned` 是**内存字典**，键是 int → 命中。
- 阶段三是**从 `_assigned/<case>.json` 读回来的**，JSON 规定字典键必须是字符串 → `pinfo.get(0)` 永远 miss。

**后果**：阶段三把**每一个 OCR 出来的引脚号/引脚名全部丢掉**，退化成位置序号 `str(k+1)`。引脚占 0.25、`net_hypergraph` 占 0.35 且键是 `(位号.引脚号)`，一处静默失效影响 0.60 的分。

修法是两形态都试 `pinfo.get(k) or pinfo.get(str(k))`。**但修完分数反而掉了**（220 张实测）：

| 阶段三的引脚号来源 | 总分 | pin F1 | netH F1 |
|---|---|---|---|
| 纯位置序号（bug 的副作用） | **7.0634** | 0.0074 | **0.1217** |
| 无脑信 OCR（修完不设门控） | 6.7986 | 0.0078 | 0.1137 |
| **只在 OCR 交出完整 1..N 排列时才信，否则位置序号** | **7.0634** | 0.0073 | 0.1218 |

**结论（反直觉但必须记住）**：我们stage1 的引脚**顺序**本身就是 GT 引脚号的强先验（真实器件多为 1..N 顺排），而 CRNN 的引脚号读数还不配打败这个先验 —— **无脑信任 OCR 让 netH F1 掉 0.0080，净亏 0.26 分**。所以现在采用最保守的门控：**只有该元件全部引脚号构成完整 `1..N` 排列时才采信，任何缺号/撞号/越界都整颗退回位置序号**。分数与「纯位置」打平，但保留了在真的整排读对时拿到正确号的能力（netH tp 2835 → 2836、net_line F1 0.0058 → 0.0059）。

这条也解释了为什么 `structmatch` 在阶段二挣来的 `pin F1 0.0069 → 0.0078` 在阶段三全部蒸发：**引脚号才是那条链的钥匙，而它现在被门控挡住了。** 想让结构化重绑定真正变成分数，得先把引脚号读数做到「整排可信」——这是下一步该投入的地方。

## 本阶段最大的一笔：`DROP_UNKEYED` —— 给不出位号就别输出这颗元件（+2.57 分）

这一节是本阶段**收益最大**的一条，而且它跟 OCR 一点关系都没有，纯粹是**读懂了官方评分口径之后改的输出策略**。

### 病根一：兜底键 `pNNN` 在 GT 里永远不存在

`assemble.py` 原来在拿不到（或撞上）位号时，会给这颗元件安一个兜底键 `"p%03d" % i`。它的代价被严重低估了：

- `metrics.py:224` `component_f1` 遍历的是 **`set(gt) | set(pred)` 的键并集**，键差一个字符就是「记一笔 `extra`」**外加**「记一笔 `missing`」。
- `metrics.py:289` 起，网络超图按 `net_pin_set(net) = frozenset(parse_hypergraph(net['hyperGraph']))` 摊平成 `(元件键, 引脚号)` 的集合，**非 exact 模式下 `fp = total_pred_pins - tp`** —— 也就是说，我们 nets 里**每一个** `(键, 引脚号)` 只要不在配对上的那条 GT 网络里，就是一个 FP。
- 而官方 GT 里 **4144 / 9425 = 44.0% 的元件键是 `∅NNN`**（`∅` 是直径符号 U+2205），类型是 `gnd 2195 / v 1143 / net_input 323 / net_short 163 / net_output 72 / other 66 / m3螺丝 58 / …`。**这个编号在图纸上一个字都没印**（证据图 `work/preview/compcases/gt_diam_zoom.png`：`∅645`/`∅674`/`∅824` 就是「3.3V」电源箭头，`∅690`/`∅753` 就是 GND 符号）。它是**整篇文档一个我们看不到的全局对象计数器**：
  - 200 个 case 的 `∅` 间隔分布 `4→1142、5→1008、10→233、9→207、7→167、…`，**只有 29.8% 的间隔是 4**，不是等差。
  - 几何序检验（200 case、73173 个配对）逆序率 `x_then_y 0.4864 / y_then_x 0.4865 / -x_then_y 0.5117 / -y_then_x 0.5133 / 按面积 0.3867`（随机 = 0.5）⇒ **与几何位置无关，不可复现**。
- `evaluate.py:114` 的官方自检注释把这条规则说得很直白：**「Copy-GT-with-a-renamed-key must lose exactly that component」** —— 改键就丢元件，这是**设计意图**，不是 bug。

⇒ **任何「我们给不出真实位号」的元件，输出它就是白送 FP（元件一笔 + 它名下每个引脚一笔）。**

### 改法

`assemble.py` 顶部新增：

```python
DROP_UNKEYED = os.environ.get("STAGE2_DROP_UNKEYED", "1") not in ("0", "false", "False")
```

`build_doc` 的元件循环里，兜底分支由「安个 `pNNN`」改成**直接 `continue` 不输出**：

```python
if not key or key in components:
    if DROP_UNKEYED:
        continue
    key = "p%03d" % i
```

**网络超图的修剪是免费附赠的**：`build_doc` 的 net 循环里 `k = keymap.get(cid)`，被丢掉的元件不在 `keymap` 里，引用它们的项自然被跳过、`hyperGraph` 自动重写。再加一条「一个引脚都没连上的 net 不输出」（它在匈牙利匹配里还可能把 GT 网络抢走）。

顺带修掉一个**真 bug**：`merge_by_label` 原来只保留 root 成员的 `_refs`，于是「按同名网络标签并起来」的 net，除第一条以外成员的 `(元件, 引脚)` 引用**全部从 hyperGraph 里消失** —— 而 `netH` 的 tp 正是按 `|pred_pins ∩ gt_pins|` 加的，合并本该让 tp 变多，旧写法反而把它们丢了。改成跨成员取并集（`base["_refs"] = refs`）。

## `PIN_STAMP` —— 引脚点位照官方图章生成（+4.90 分）

**背景**：把 `pin_f1`（`metrics.py:255`）的损失拆开（`work\tools\diag\_pin_why.py`，220 张、
GT 引脚 22696）得到：`ok 167 (0.0074)` / `key_miss 15125` / `num_miss 3008` / `name_bad 1384` /
**`point_bad 3012`** / `pred_extra 5613`。而 `point_bad` 的距离分档是
`<=10px 47 / <=20px 29 / <=40px 1608 / <=80px 1009 / >80px 319` —— **不是抖动，是 40px 量级的
系统性偏移**；两脚元件的 pin_1/pin_2 交换率 **0.829**。

**根因**：官方 GT 的引脚点位**不是走线接点**，而是「元件 bbox 中心沿符号主轴 ±SPAN」的
理想图章点 —— `schematic_parser/stamp.py` 把每个类固化成一个小图章，两个引脚就贴在中心
两侧。例：`0001 C14` GT bbox `[504,120,520,140]`、中心 `(512,130)`，GT `pin_1=(512,110)`、
`pin_2=(512,150)`。我们原来的点位来自 stage1 的导线附着点，实测与 GT 点 p50 = **39.9px**（r/c）
—— 正好错了一个符号长。而官方判分是「点位距离 <= `pin_tol`（5px）」，所以那 3012 条全丢。

**从 220 个官方 case 实测出来的图章表**（`work\tools\diag\_pin_stamp.py`）：

| 类型 | 轴向 | `pin_1` 一侧 | SPAN | 纯度 |
|---|---|---|---|---|
| `r` / `c` / `l` | bbox 竖长 → y，否则 x | **−** | 20 | **1.00**（r 853/715、c 1287/342、l 27/88） |
| `fuse` | 同上 | **−** | **21** | 1.00 |
| `crystal_2pin` | **与 bbox 长短边垂直** | **−** | 20 | 1.00 |
| `d` | 同上 | **+** | 20 | 0.68 / 0.74 |
| `led` | 同上 | **+** | 20 | 0.68 / 0.90 |

⚠️ **判轴必须用贴章前的框**：`STAMP_SIDE` 把每个类都换成了**正方形**图章
（r/c/d/led/pin/testpoint/gnd = 20、l = 34、fuse = 22、crystal_2pin = 15），
所以 `bbox_json` 的长短边信息**已经被抹掉了** —— 实测用贴章后的框判轴命中率只有
**0.630**（对 r/c/l 就是瞎猜），用贴章前的 raw 框是 **0.955**。

**所以第一步是让 stage1 把贴章前的框带出来**：`stage1/detect.py` 里
`d["box_raw"]` 本来就有（在 `snap_box` 之前、1 行），现在多发一个
`bbox_raw_img` 字段。YOLO 的训练标签来自官方 json 的**未贴章**框，所以它的 raw 框长短边
是可信的。`stage1` 全量重跑一次（`--imgsz 1600 --workers 4`，99.8 s）即可。

**第二步是 `stage2/assemble.py` 的 `stamp_pins()`**：对 `PIN_STAMP_TYPES` 里的类，
将每个观察到的附着点按几何侧映射到 `pin_1` 或 `pin_2`，点位按已有图章约定给出。
同侧重复附着点发布为同一个引脚，同时保留全部原始索引到该引脚的映射，供碎线网络闭包使用；
只有一个端子的接点时不补出另一端。这一步决定了 net 超图里 `(元件键, 引脚号)` 对不对得上。
以前 stage1 给 3 个附着点时我们会输出 `pin_3`（R15 就是这样），现在被结构性地消掉了。

`STAGE2_PIN_STAMP=0` 可以关掉退回旧行为。

### 二、四个真 bug（每一个都是「不修就会静默错」的那种）

**1. `torch.device("0")` —— 会让整个提交跑出零位号（最严重）**

提交驱动把 `-device 0` 原样喂给 torch，而 ultralytics 收 `"0"`、`torch.device("0")`
直接抛 `RuntimeError: Invalid device string: '0'`。`TextEngine.allow_missing=True`

但 component F1 会掉到 0。

修法是在最深处收口：`Y:\workspace\EDA\eda-pcb\textrec\infer.py` 新增
`normalize_device(device)`，把 `"0"`/`"0,1"`/`"0:1"` 翻译成 `"cuda:0"`，
`auto`/`""`/`None` 走 `torch.cuda.is_available()`，没卡时安静退 CPU。
`Recognizer.load` 改用它。**冒烟复核：位号 0/0/0 → 33/3/5。**

**2. `canon_designator` 的 `Rl4` → `R14` 支在 `strict` 下返回 `""`**

### 1. `STAGE2_BOX_PIN_PARTIAL`：`box`(IC) 的引脚号不再「一个读废、全颗作废」（+0.288）

`assemble.py` 原来对 `box` 的引脚号是全有全无的：`all(n.isdigit())` 且互不相同且都在
`1..999` 才采信，否则整颗 IC 退回位置号 `1..N`。一颗 72 脚的 IC 里只要**有一个号读成空、
读成 `l`、或者跟别人撞号**，其余 71 个正确的号也一起作废。

而 `PinF1` 只在 `box`(IC) 上算分（官方评测 Q2：「非box类型元器件 pin name, pin number
不参与评分」），所以这等于把唯一算分的引脚全扔掉 —— 实测引脚号读到率只有 **0.272**，
344 个键命中的 box 元件里 GT 4064 个引脚我们只对上 **1046（0.257）**。

改成**逐引脚**采信（`BOX_PIN_PARTIAL = os.environ.get("STAGE2_BOX_PIN_PARTIAL", "1")`）：
某个号只要是 `1..999` 的整数、且没跟同一颗 IC 里别的采信号撞，就用它；其余用位置号补，
并避开已经用掉的号（保证 `pin_*` 键不撞）。**全对时输出与旧行为逐位相同**，所以这个改动
严格弱优于旧行为。

### 两个最关键的机制（否则就是负收益）

1. **「位号一致」门控是「值」通道的命门。** 不加门控、一律覆盖是 **−0.316**
   （`valonly` 23.6404）；在**键已经匹配上**的 r/c 上比，VLM 值 0.7050 vs 管线 0.5025，
   但 VLM 有约 1/3 的读数**读到了邻居**。只采纳「模型自报位号 == 该元件键」的读数后，
   精度 0.7050 → **0.7950**（scale 4），端到端从 −0.316 翻到 **+0.949**。
2. **值通道可以顺手把 `pNNN` 兜底键换掉。** 兜底键**永远不可能**与 GT 对上
   （`unkeyed_match='gt'` 只放行 GT 自己的 `∅NNN`），所以拿模型自报的位号去换**有赚无赔**：
   `renamed 298 → 854`、`missing 3019 → 2583`、**+0.369**，零额外 VLM 调用。
   代价是 `bbox_mismatch 255 → 393`、`type_mismatch 79 → 101`（换错了键的那些），净值仍是正。

## 2025-10-05（深夜）—— `STAGE1_SPLIT_JUNCTIONS`：T 形分叉处切段（**+0.0558**，已默认开）

`stage1\wires.py` 的 `_rebuild_nodes` 一直报出 `junctions: 0` —— pskel 的 `snap`
会把一条走线接成一整段，即使它中间经过一个 T 形分叉，于是「>=3 条线段共用端点」
的情况一次都不出现，而官方 GT 的边是在分叉处切开的（`0001` GT 340 条边 vs 我们 153）。

新增 `_split_at_nodes(segments, tol=1.5)`：**任何「别的线段的端点」落在本条线段内部
（垂距 <= tol）就在那里切开**。`STAGE1_SPLIT_JUNCTIONS` 默认 `1`（设 `0` 关）。
它是**严格增加候选**的一步：端点只会变多、不会移动，而官方 `net_line` 的判据正是
「同一 net 内两条边的端点距离 <= 5px」。

第一次这么比出来的「+0.028」其实是运行噪声。
