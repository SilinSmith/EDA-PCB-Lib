# stage1 —— PNG → 第一阶段的中间结果

这一层把「一张原理图 PNG」变成**带多假设、已和导线几何挂上钩的元件清单**，
就是讨论里说的**第一阶段**：墨迹介导定位 + YOLO/CV 检测 + 与导线墨迹联合解算。

它**不做**第二阶段（文字识别、位号绑定、LLM 全局指派），也**不做**最终 JSON 组装。
名字（`key`）在这一层一律留 `None`，由后面的文字线（`eda-pcb/textrec`）+ 绑定负责。

```
PNG ──┬─► detect.Detector ──► YOLO 43 类（贴规范图章）
      │        └─► cvparts.* 专类 CV 检测器 ──┐
      │                                       ├─► cvparts.hypo 多假设槽位
      ├─► cvparts.textbox ──► 文字框（只定位，不识别）
      └─► wires.extract_wires ──► pskel 骨架 ──┴─► pipeline.attach
                    ▲  涂掉元件框、涂掉文字框
                    └── 大尺度连通 / 轴向 / 去边框 过滤
                                                          │
                                                    <case>.stage1.json
                                                          │
                                                  (可选) llm.arbitrate
```

## 导线提取：五条已验证的过滤，和四条被证伪的

原理图上的墨迹一视同仁 —— IC 矩形边框、电容极板、引脚名文字、标题栏文字、
图纸边框，全都是细笔画。所以骨架化出来的东西远多于走线：**不处理时提取总长是
GT 网表的 5.04 倍、只有 6.1% 压在真导线上。**

**已验证有效（都已落进 `wires.py` / `pipeline.py`，全量复测过）：**

| 手段 | 参数 | 效果 |
|---|---|---|
| **遮挡已检出元件** | `occlude=[bbox_img...], occ_pad=2.0` | 用四角中位色当背景涂掉元件框 |
| **涂掉文字框** | `erase=[textbox...], erase_pad=1.0` | 文字笔画与导线同形，必须先减掉；见下 |
| **去掉图纸边框** | `drop_frame=True` | 贴近页边且很长的轴对齐线段 |
| **轴向过滤** | `max_axis_dev=12.0` | 与最近 0/45/90/135 度的偏差 |
| **大尺度连通 + 邻域豁免** | `min_extent=80.0, rescue_pad=8.0` | 见下；豁免区**同时包含元件框与文字框** |

五条逐个叠加：精度 0.0613 → **0.2672**（4.4×）、F1 0.1025 → **0.2701**（2.63×）、
总长比 5.04× → **1.954×**。元件指标完全不变，管线反而更快（70.9 → 50.7 s）。

### 一个必须记住的实现坑：`rescue_pad` 的豁免区要包含**文字框**

文字一旦被涂掉，导线就在那里被切断，两截都可能小于 `min_extent=80` 而被整条丢掉 ——
实测 KiCad 上 P 0.182→0.094、R 0.219→0.129。修法是把 `erase` 的框也用
`pad2 = erase_pad + rescue_pad` 画进豁免掩膜。修完导线 F1 0.2334 → 0.2630 → **0.2701**。

### 假阳性归因（`work/stage1_wire_attrib.py`，全 220 张、51267 段）

每条非 TP 线段按中点归类，并统计它到最近 GT 线段的最差采样距离：

| 类别 | 条数 | 占比 | 总长占比 | 到 GT 距离 p50 |
|---|---|---|---|---|
| TP | 13701 | 0.267 | 0.244 | **1.4 px** |
| comp（贴已检出元件框 ±3px） | 1717 | 0.033 | 0.022 | 22.7 px |
| text（贴文字框 ±3px） | 8384 | 0.164 | 0.099 | 31.4 px |
| **frame（页边 3% 或标题栏区）** | 7616 | 0.149 | **0.265** | **189.7 px** |
| other | 19849 | 0.387 | 0.370 | 25.5 px（len p50 只有 10.2px） |

⇒ **除 TP 外每一类都离 GT 22~190px，全是真的非导线墨迹，不是"偏了一点的真线"。**
按来源：jlc `frame` 占 0.248、kicad 0.214（这两类图幅大、标题栏表格线多）。

### 大尺度连通：文字与导线的结构性区别

用户给的关键先验：**导线是一个大尺度连通体**（沿延伸方向能走很远，或者有 L/T/十字分叉），
而文字笔画是孤立的小团。实测墨迹连通分量的分布证实了这一点：

| case | 墨迹分量 | ≥50px | 最大 extent | p50 | p90 |
|---|---|---|---|---|---|
| 0101 jlc | 740 | **19** | 1434 | 10 | 18 |
| 0001 KiCad | 2096 | **6** | 1782 | 10 | 14 |
| 0059 Datasheet | 65 | 1 | 805 | 22 | 26 |
| 0011 Altium | 2687 | 27 | 4133 | 19 | 26 |

**文字是一大片 extent 10~30px 的小团，导线是少数几个大连通体。**
实现要点（两个都踩过坑）：
1. 分量必须在**墨迹掩膜**上算，不能在骨架上算 —— `zhang_suen` 会在 1px 细线处断连，
   骨架分量比墨迹分量碎得多（0101 609 个 vs 740 个，0001 1182 个 vs 2096 个）。
2. 采样要打在**膨胀 3×3 后的墨迹**上 —— RDP 后的线段是折线的弦，中点常偏离 1px 骨架。

**只做 extent 会伤 jlc**（0101 0.223→0.187）：那种风格靠 net label 表达连通，
GT 的边本来就是「引脚到标签」的短桩，本身就在小分量里。用户的第二句话修掉了它 ——
**导线是用来连接元器件的**：分量再小，只要线段端点落在「已检出元件框外扩
`occ_pad+rescue_pad`」内就仍然保留。`ext>=80 + rescue 8` 在 6 个 case 上
**全部优于**不设门槛的基线：

| case | 基线（遮挡+框+轴12） | 只加 ext>=50 | **ext>=80 + rescue 8** |
|---|---|---|---|
| 0101 jlc | 0.2232 | 0.1874 | **0.2521** |
| 0107 jlc | 0.0964 | 0.0898 | **0.1114** |
| 0001 KiCad | 0.1583 | 0.1610 | **0.1649** |
| 0059 Datasheet | 0.1928 | 0.2485 | **0.3152** |
| 0050 Altium | 0.2159 | 0.2760 | **0.2953** |
| 0011 Altium | 0.0363 | 0.0441 | **0.0494** |

四条**被证伪、不要再试**的：

1. **长度过滤（segment 级与 polyline 级都不可用）。** 真实导线被 `pskel` 的
   snap/结点切碎成长度 <20px 的碎片，任何长度门槛都会连真导线一起删 ——
   0101(jlc) 上 `min_len=10` 或 `poly>=20` 都把 F1 从 0.191 打成 0.000。
   它只对 datasheet/Altium 这种大而干净的图有效（0059 0.169→0.307）。
2. **颜色可分性。** 覆盖 50% 真段时精度只提升 altium 3.47× / kicad 4.39× /
   jlc 2.57× / datasheet 1.39×，都不够。
3. **按"分量包围盒横跨整图"删图框（`work/_frame_ab.py`）。** 37566 个假阳性里只删掉
   约 190 个，F1 0.3079→0.3086。原因：标题栏表格线**不是一个连通分量**，每条线在
   tol=2px 下各自成组，跨度判据打不着。想治 `frame`（占总长 26.5%）必须换**线段级**
   的结构判据。
4. **加大 `erase_pad`（1.0→3.0）。** 文字残渣确实掉 62%（8384→3207 段），但贴着网络
   标签的真导线被一起涂掉：F1 **0.2701→0.2326**，五个来源全下降
   （altium R 0.344→0.237、datasheet 0.622→0.450、jlc 0.125→0.095、kicad 0.152→0.106）。

### 悬空交叉校验：实现完了，但杠杆很小

`reconcile.py` 把导线按端点连通性（**tol=2px，不能用严格相等** —— pskel 的 rdp+snap
让端点有 1~2px 误差，按 tol=0 建图会把整条走线拆成几百个几像素小分量）分成组，
再判断每组端点是否落在某个元件框或文字框附近。全 220 张实测：

| 臂 | R | P | F1 |
|---|---|---|---|
| base | 0.2730 | 0.2672 | **0.2701** |
| 删全悬空（无文字锚） | 0.1750 | 0.2851 | 0.2169 |
| 删短悬空<80（无文字锚） | 0.2173 | 0.2763 | 0.2433 |
| **删短悬空<80（有文字锚）** | 0.2641 | 0.2810 | **0.2723** |

**结论：没有文字定位时，"悬空"根本判不了**（真导线端点大量落在网络标签文字上，
只有元件框一个锚点会把全部真导线误判成悬空 —— 悬空元件数 75 → 1）。加上文字锚之后
删除只剩 **+0.0022**，几乎中性。全库悬空元件只有 **40 个**
（gnd 18 / r 8 / net_short 7 / c 4 / amp_3pin 1 / box 1 / v 1，全部来自 YOLO）。
嘉立创 logo 并没有被 YOLO 当成元件，所以也没有"靠悬空删掉伪元件"的收益。

> **这条规则真正的价值是逼出了文字定位** —— 为它写 `cvparts/textbox.py` 带来了导线
> F1 +0.037（0.2334→0.2701），远大于规则本身的 +0.002。

### 一个造成"凭空大尺度斜线"的一行 bug（已修）

`pipeline/pskel.py:469` 原本是 `seg = p.pts if cur.end == 1 else list(reversed(p.pts))`，
**两个分支都反了**。`cur.end` 是进入这条 path 的那一端，按 `_dir_at` 的约定
（`from_end=0 -> leaving walk[0]`）`end==0` 对应 `pts[0]`。方向反了之后，每次
`chain.extend` 都会把上一链尾接到这条 path 的**另一端**，产生等于该 path 长度的瞬移：
轴对齐的瞬移变成凭空多出的图纸边框长线，**斜向瞬移被 `snap_polyline` 吸附成精确 45°**，
于是伪装成"大尺度斜线"并躲过 `max_axis_dev=12` 的检查。

修法与验证见 `work/_trace_jump.py`（复刻并链循环 + 记录 >30px 跳变）和
`work/_diag_chain2.py`（修前 0101 有 2 条 45° 长斜线、0107 有 17 条；修后两者均为 **0**）。
导线 F1 0.2198 → **0.2334**。

### 为什么导线这么难：源图是 1px 细线

把 GT 的每条 edge 栅格化后到原图上采样：

| 采样线宽 | 压墨率 @ 平移 (0,0) |
|---|---|
| **1 px（真实线宽）** | **94.1%** |
| 3 px | 46.8% |
| 5 px | 35.2% |

两个结论：

- **坐标约定完全正确**，`(0,0)` 就是最优平移；
- **GT 的 `net_line` 是「画出来的走线」的忠实记录**（94.1% 压在墨上），
  不是理想化连接 —— 所以 0.18 的 F1 是**真实的能力差距，不是尺子坏了**。

同时这也解释了 `pskel` 为什么碎片化：源图走线本身就是 1px 发丝线。
GT 的 33037 条 edge **100% 都是 2 点直线**，中位长度只有 22px。

## 元件引脚介导的贪心射线（`pintrace.py`）——导线这一环最大的单笔收益

### 为什么全局骨架一定漏

骨架 + 过滤这条路，判据天生是「长 / 直 / 大连通」，于是三类**真导线**被系统性丢掉：

* 被文字涂断的（涂掉处两截都变短，过不了 `min_extent=80`）
* 走线穿过元件符号时被遮挡的（同理）
* 本来就短的小分量（jlc 风格靠 net label 连网，GT 的边就是「引脚 → 标签」的短桩）

反过来看，**起点是确定的**：导线是用来连接元器件的，每条导线一定从某个引脚出发，
而且方向由引脚给定。所以从引脚沿法线一步一像素地跟着墨走，直到墨断掉 —— 文字带不偏它。

**关键实现选择：射线跑在原始墨迹上，不涂文字、不遮挡元件。**
涂文字是为了让*全局*方法少提假阳性；方向已知时不需要，反而会伤害它。

## 引脚与网络（`pins.py` + `nets.py`）：补上 0.70 分的**结构**缺口

在这两个模块之前，`stage1` 的产物里**一个引脚点、一个网络都没有** —— 而官方评分里
`pin 0.25 + net_hypergraph 0.35 + net_line 0.10 = **0.70**` 全部以引脚点为最小单位。
也就是说那 0.70 分不是「做得不好」，是**结构上拿不到**。现在补上了：

    段  --(labels.wire_groups)-->  连通分量
    元件框 --(pins.find_pins)-->  引脚点
    引脚点 --(最近段 <= 12px)--> 挂到某个分量
    一个分量 + 挂上来的引脚 = 一个 net

### 引脚几何先验（220 张 GT 实测，`work/gt_pin_geom.py`）

| 事实 | 数值 |
|---|---|
| 引脚在框内 | **0.0%** |
| 引脚到框边距离 p25 / p50 / p75 | **9 / 10 / 10 px** |
| `<=12px` / `<=24px` | **86.1%** / 97.8% |
| 落边分布（left/top/right/bottom） | 10622 / 5528 / 3913 / 2628 |
| 每条元件引脚数 p50 / mean | 1 / 2.36 |
| `box`（IC）的引脚 | 贴左右**长边**外侧约 10px（left 4268 / right 3577） |

两条已对照 GT 验算的规则：

1. **两脚元件**（r/c/l/d/led/fuse…）的两个引脚在**长轴方向**、离中心 `L/2 + 10`。
   GT 例 `R5 = {"type":"r","bbox":[208,340,216,360]}` → 引脚 y=330/370，中心 y=350，`20/2+10 = 20` ✓
2. `∅202 = {"type":"v","bbox":[1074,286,1084,296]}`（10×10 方框）→ 引脚离中心 `15 = 10/2+10` ✓

⚠️ **别用「最近边」判两脚元件的引脚在哪条边**：R5 的引脚离左右边只有 4px、离上下边 10px，
取最近边会判成「左边、沿边位置 −0.5」。要用长轴判据。

### 方法：导线触到框边的位置

原理图的基本画法就是「导线画到引脚处就停」，所以**接触点**就是引脚。三个关键实现点：

1. **对框边求距离，不是对实心矩形** —— 否则框内部远处的点距离也是 0，整个框内的东西
   都会被当成接触点；
2. **段要按 3px 密集采样**，不能只看端点 —— 串联元件的那根线是**从框中间穿过去**的；
3. **接触点必须朝框外推 10px 才是引脚** —— 接触点在框边上（误差 0px），GT 引脚在框外
   10px；不推的话每个引脚都差 10px，而 `pin_tol` 默认只有 5px，会**全判错**。

一根导线都没触到时才走类型先验兜底（只有一半引脚会接线）。

`pins.py` 自带 **10 条合成自检**（`python stage1\pins.py`）。第一次跑有 1 个 FAIL —— 用例是
「线**沿着**左边界画」，我期望得到线的起点 `(90,200)`，实得 `(90,160)`。**是测试写错了**：
整段贴边时它本来就是一个「沿边的长接触」，取中点是合理行为。自检给出的是非黑即白，
真实数据给的是说不清对错的数字 —— 这个项目里已经是第四次「测试错、代码对」。

### 为什么 `box` 只有 0.341 —— 已诊断，是两个**有上限**的原因（`work/_box_pin_diag.py`）

40 张 / 136 个 box / 1517 个 GT 引脚：

| 读数 | 值 | 含义 |
|---|---|---|
| GT 引脚 → 最近提取段采样点 | p50 **1.2px**，`<=3px` 78.9%，`<=6px` 85.2% | **墨迹是够的，段画到了引脚上** |

两个候选解释都**被证伪或证明收益很小**：

- **不是元件定位误差**：把检测框换成 **GT 的框**再做一遍，`box` 的 R 从 0.472 变成
  **0.449**（整体 F1 0.5637→0.5828，只有 +0.019）⇒ 定位误差不是 `box` 的瓶颈。
- **不是接触半径**：扫 `touch_tol ∈ {6,10,14,20} × cluster_r ∈ {12,7}`（40 张），最好的
  组合也只到 F1 **0.5651**（基线 0.5637）。`cluster_r` 调小会把 R 抬 0.03、同时把 P 压
  0.04，净效果为零。

⇒ 剩下的是「固定 10px 外推 vs 实际 3~23px 偏移」+「聚类半径并掉 23% 的相邻引脚」，
两个都是**有上限**的（合起来大概 +0.05 F1），**不是 2 倍量级的杠杆**。真要提 `box`，

### 结构性天花板：这 0.70 分要等第二阶段

官方 `pin_f1` 的键是 `(component, pin_number)`，`net_hypergraph` 的键也是
`(component, pin_number)`，并且两者都要求 `pinname` **字符串严格相等**；元件还要靠
位号（`key`）匹配，而 `key` 现在**全是 `None`**。

引脚号 / 引脚名 / 位号**只能来自 OCR**（第二阶段 `eda-pcb/textrec/`）。所以：

- `pins.py` + `nets.py` 解决的是「**结构上有没有引脚和网络**」—— 这一条已经完成；
- 「**这 0.70 分能不能拿到**」取决于 OCR，以及导线图能不能从 67% 单引脚网络里走出来。



动机是那个 34%：同 net 的引脚有一批纸上没画线，靠 net label 按名字逻辑相连。
「逻辑合并」本身只值一句 `group by 标签文本`，难点全在**先把标签定位出来**。

语义：网络标签总画在一条走线的**自由端**（只挂一条段的那头），不会画在走线中段。
所以 `stage1/labels.py` 的 `label_candidates(segments, texts, boxes=...)` 做三件事：
并连通分量 → 找自由端 → 每个自由端找 `max_dist`（16px）内最近的文字框。两道门控
是必须的，不然候选会膨胀到文字框总数的 63%（每张 199 个）：
  1. **锚定**：这条分量必须碰到某个元件框（`ANCHOR_DIST=6`）——一条走线一头接元件、
     另一头才是标签；
  2. **排除元件内的文字**：位号 / 参数 / 引脚名画在框里或紧贴框边，不可能是标签。

判据（`work/stage1_label_eval.py`，只用官方 GT）：GT 每条 `net_line` 的两个端点里，
落在某个 `pins[*][*].point` 附近的算**引脚端**，其余算**标签端**（标签画在那儿）。
候选的自由端与 GT 标签端一对一贪心配对（6px）即 TP。

**实测 30 张（`stage1_all13`）：**

| 配置 | 候选/张 | TP | P | R | F1 |
|---|---|---|---|---|---|
| 全部段，`min_group_len=0` | 70.4 | 179 | 0.0848 | 0.0649 | 0.0735 |
| 全部段，`min_group_len=16` | 47.8 | 168 | **0.1172** | 0.0610 | **0.0802** |
| 只用骨架段（切掉射线） | 45.5 | 90 | 0.0659 | 0.0327 | 0.0437 |

**根因是段图太碎，不是门控没调好。** 一张图平均 324 条段，却并出约 211 个连通分量、
**422 个自由端** —— 大部分段是孤立的，射线的端点又几乎全落在空白里。于是「自由端」
根本不等价于「走线的端」：

| 候选自由端的位置 | 占比 |
|---|---|
| 落在真走线端点上（≤6px） | 25.2% |
| 在走线上、但不在端点（≤2px，射线/骨架停在走线中段） | 21.1% |
| 落在空白（到最近 GT 走线 > 20px） | 26.8% |
| 落在 GT 引脚点上（本该是引脚连接，不是标签） | 13.9% |

到最近 GT 走线的距离：p10 1.0 / p25 3.6 / **p50 11.0** / p75 21.0 / p90 33.2 px。

⇒ **结论：在导线图被整合到「自由端 ≈ 真实走线端」之前，标签定位没有意义。**
两条路可以走，都需要先动导线图本身：(a) 把骨架的毛刺分支剪掉、把 1~2px 的断口沿
方向桥接，让自由端数从 422 降到接近真实的走线端数；(b) 干脆不用自由端，改成
「文字框 → 是否网络标签」的分类问题，但那要等第二阶段的文字内容。

顺带得到两条有用的读数：GT 走线端点里 **52.8% 是标签端**（每张约 92 个），
所以这条线的存量是真实的、不是判据造出来的。

## 三个把我误导了半天的评测器 bug（已修，教训写在这里）

那一轮「60 张消融说锚点截断最优、端到端评测说它最差」，方向完全相反。查下来
**三个 bug 全在我自己写的评测器里**，不在算法里：

1. **`stage1_conn_eval.SegIndex.nearest`（网格索引）静默漏找真实最近段。**
   同一份产物、同一批 case：`all11` 暴力 R **0.7889** vs 网格 R **0.1297**；
   `all12` 暴力 **0.6325** vs 网格 **0.0663**。网格路径低报约 **6 倍**。
   **禁止再用网格索引做最近段查询**，一律用 `_dist_pts_to_segs` 的全矩阵 argmin。
2. **`build_groups` 规则 (2) 的端点索引写错，把整张图塌成一个连通分量。**
   `np.concatenate([segs[:, :2], segs[:, 2:]], axis=0)` 把第 i 段的两个端点放在
   第 i 行与第 i+N 行，而循环按 `D[2*i+e]` 取值 ⇒ 读到的是**下一段**的端点，
   它到「自己那条段」的距离恒为 0 ⇒ 每一段都无脑与其序号后继并起来。
   抓它的是**合成自检**（三段相隔 100px，返回值该是 3 个分量而不是 1 个）。
   症状指纹：连通 R 恰好等于「两个引脚都绑上了」的比例，连通 P 塌到 0.014。
   修法：`np.stack([segs[:, :2], segs[:, 2:]], axis=1).reshape(-1, 2)`，
   配 `own = np.repeat(np.arange(n), 2)`，并把每行自身置 `np.inf` 再 argmin。
3. **（最隐蔽）`stage1_wires_eval.dist_pts_to_segs` 返回 `(M,)` 而不是 `(M,N)`。**
   它算的是「每个点到**最近那一条**段的距离」。而调用处写的是
   `d = dist_pts_to_segs(np.asarray([pt]), psegs); j = int(np.argmin(d))` ——
   **长度为 1 的数组上 `argmin` 恒等于 0**，于是所有引脚都绑到第 0 条段，
   整张图再次塌成一个分量。**整个「连通」列因此全是垃圾。**

教训：**评测器的每个数字都要有一个合成自检**（构造已知答案的小例子），
真实数据上的数字不对时会静默地看起来很合理。

读法：**每一道图像级过滤都在花连通性买覆盖率**（raw 0.1631 → 加遮挡 0.1561 →
加涂文字 0.0894 → 加轴向 0.0751）；**射线是唯一的大杠杆**（full 0.0748 →
full+rays 0.2439，3.3 倍）。按官方权重 `0.35×连通 + 0.10×覆盖` 折算，带射线的臂
全落在 0.127~0.133，不带射线只有 0.052~0.068。

### 锚点截断：用户的直觉没错，但实现方式是净亏，已撤掉

`pintrace.trace_from_boxes(..., anchors=..., clip_anchors=True, require_anchor=True)`
试过「射线碰到元件框或文字框就截断、走到尽头没碰到锚点就整条丢」。60 张上
连通 F1 0.1270（截断到锚点）/ 0.1504（只截断不丢弃），**都不如不截断的
`full+rays` 0.2439**；全量端到端连通 R 从 0.1566 掉到 0.0826。根因是
`require_anchor=True` 把「引脚 → 空白处 net label」这类最像真导线的射线整条丢掉，
引脚未绑定率 14.9% → 26.6%，连通召回腰斩。**判据错在「锚点」的定义**：应该是
「另一个引脚 / 结点 / 已确认的 net label」，而不是「任意元件框或文字框的邻近」。
要重做这条，得先把引脚 tip 与结点提准。

## 并行：为什么是进程池而不是线程池

- `pipeline.pskel` 是纯 Python 循环 + numpy，**被 GIL 绑死**；线程给不了加速。
- 一个 `YOLO` 实例并发 forward 不安全；每进程各持一份模型最省事。
- 所以 `--workers` 是 `ProcessPoolExecutor`；线程池只用在该用 IO 的地方（`llm.py`）。

## 已知限制（诚实清单）

1. **导线精度 0.242 / 召回 0.683 / F1 0.3569 / 连通 F1 0.2454** —— 第一阶段最大的缺口。
   连通口径下**几何天花板只有 0.658 / net 完整率 0.598**（拿 GT 自己的走线当段集合），
   我离它 4.2 倍；剩下那 34% 要靠网络标签。
   剩余假阳性归因（骨架那部分）：`frame`（图纸边框 + 标题栏表格线）**占总长 26.5%**、
   `text` 占 9.9%、`other` 占 37%（长度 p50 只有 10.2px 的碎段，多半是元件引脚桩与骨架毛刺）。
   已经排除的解法见"被证伪"五条；还没试的是**线段级**的表格线结构判据。
2. **网络标签定位目前不成立**：候选 P 0.117 / R 0.061（30 张），根因是段图太碎
   —— 一张图 324 条段却并出约 211 个分量、422 个自由端，"自由端"不等价于"走线端"。
   要动导线图本身才能往下走，详见「网络标签定位」一节。
3. **文字只定位、不识别**：`cvparts/textbox.py` 在 5 张上做过引脚名覆盖率自检
   （@20px 0.9864），**尚未跑全 220 张**；平均 567 框/张、412 ms/张。
   它的精度还没在官方 GT 上量过（只有召回下界）。
4. **`testpoint` 的 `dot` 画法关掉了**（`cvparts/testpoint.py: ENABLE_DOT=False`）。
   官方 220 张里 43 个 testpoint 分三种画法：`ring3` 20 个、`hole` 12 个、
   `dot` 11 个。dot 的门限只要放到能吃到 1 个真例，误报就是 **8497 个（38.6 张/图）**
   —— 圆点和字母碎片、连接器圆点、过孔同构。所以 dot 这 11 个实例目前检不出。
5. **导线附着是贪心的**（`max_dist=24px`，取最近 3 个），没有做电气一致性校验。
   附着 R 0.785 / P 0.725（tol=12px）；KiCad 只有 R 0.455 —— 它的引脚在 IC 矩形边上，
   而我们跑骨架前把元件框整块涂掉了，贴着框的那截引脚桩就没了。
6. **`key` 全是 `None`**。引脚与网络**已经生成**（`pins.py` / `nets.py`），但官方的
   `pin_f1` / `net_hypergraph` 要求 `(component, pin_number)` 的键与 `pinname` **字符串严格
   相等**，而引脚号 / 引脚名 / 位号**只能靠 OCR**（第二阶段 `eda-pcb/textrec/`）。
   所以现在能拿的分仍然接近 0：**几何位置的门槛过了（引脚位置 F1@8px 0.5730），
   拿分的门槛没过**。
7. **网络 67.1% 只有一个引脚**（220 张、14554 个网络），因为导线图太碎。`nets.py`
   目前的作用是把输出结构补齐，还不是「能用的超图」；和连通 F1 0.2454 是同一件事。
8. **`box`（IC）的引脚位置 R 只有 0.341 @8px**，而它占全部 GT 引脚的 42%。已诊断：
   墨迹够（GT 引脚到最近段 p50 1.2px），不是定位误差（换 GT 框后 0.449），不是接触半径
   （扫 8 个组合最好 0.5651 vs 0.5637）。是两个**有上限**的原因：固定 10px 外推 vs 实际
   3~23px 偏移、`CLUSTER_R=12` 并掉 23% 的相邻引脚。要再提得走「IC 引脚等距排布」的
   结构化解法，别再调这两个阈值。
9. **`pins.py` / `nets.py` / `labels.py` 的自检必须常跑**（`python stage1\pins.py` 10 条、
   `python stage1\nets.py` 9 条）。**LLM 通路未经真实端点验证**：`llm.available()` 只检查环境变量，没打过真实请求。
10. 阶段一的输出**还不是提交格式**，需要第二阶段的位号/引脚/网络才能组装。
11. `pipeline.attach` 的接线率 9381/9559 = 98.1%；过滤掉更多导线后这个数会下降，
   这是预期行为，不是 bug。
12. **注意 `stage1_conn_eval.py` 与 `stage1_filter_ablation.py` 的历史**：这两个
    评测器各被三个 bug 坑过（网格索引 / 端点索引 / 返回形状），修好后 `all11` / `all13` /
    `all14` 的连通数字才可信。**任何新写的评测函数都要带合成自检。**

## 检测这一环的两处修正：NMS 与 imgsz

### 1. ultralytics 自带的 NMS 不够用，我们一直没自己再跑一遍（已修）

用户 m07122 报告「一个 GND 明明检出了却被算成多检」。查下来**不是数据集问题**：
0003 里 `c0006` 与 `c0018` 都是 `gnd`，原始框 `[297.3,2657.1,312.2,2674.5]` 与
`[297.2,2658.1,316.5,2675.4]` 的 **IoU = 0.7025**，而 `model.predict` 自带的 NMS 默认
`iou=0.7` —— 这个值正好压在阈值上，两个都活了下来。

`detect.py` 早就有自己的 `nms(dets, iou_thr=0.6)`（同类、score 降序贪心），但它**只在
tiler 分支被调用**；整图分支 `raw = self.raw(bgr, conf)` 直接吃 ultralytics 的结果。
现在两个分支都过一遍：

```python
NMS_IOU = float(os.environ.get("STAGE1_NMS_IOU", "0.5"))
...
raw = nms(raw, NMS_IOU)                 # tiler 分支
raw = nms(self.raw(bgr, conf), NMS_IOU) # 整图分支
```

**220 张实测（`work/stage1_nms50`，墙钟 57.7 s）**：

| | 改前（`stage1_all14`） | 改后 |
|---|---|---|
| 元件总数 | 9559 | 9377（−182） |
| 召回 | 0.9612 | 0.9602（漏检 373→382） |
| 多检 | 323 | **150** |
| 其中「与另一个我们的框 IoU≥0.5」的自我重复 | 192（59.4%） | **13（8.7%）** |
| 精度 | 0.9662 | **0.9840** |

代价是多丢 9 个真框（相邻小符号被合并），换来一半以上的多检消失。

### 2. `imgsz=1600` 是这一环的正解（100–200px² 那一档的病根）

`work/tools/diag/_det_why.py` 把 220 张的漏检按 GT 框面积分档，发现**「小规模识别抽风」
集中在 100–200 px² 这一档**（约 10×14 到 14×14）：3016 个 GT 里漏 210 个，
占全部 373 个漏检的 **56%**。

`--no-wires` 扫描（conf 0.20，全 220 张）：

| imgsz | 总召回 | 100–200px² 档召回 | 多检 | 墙钟 |
|---|---|---|---|---|
| 1024 | 0.9653 | 0.938 | 191 | 16.9 s |
| **1600** | **0.9845** | **0.981** | 237 | 17.2 s |

⇒ 用 **imgsz 1600**。

### 3. 自查用的判据必须跟官方对齐（IoU≥0.5 是错的尺子）

官方判据是 `schematic_parser/stamp.py:12` 的 **`max(|pred[i]-gt[i]|) <= 20`（四角差）**，
不是 IoU。而 `stage1` 自己的标签匹配、`work/tools/eval/fn_fp.py` 一直用 **IoU≥0.5**。
GT 图章框比符号小得多（**`r` 只有 8×20，符号实际约 24×65**），在 8×20 上 IoU≥0.5
只容忍中心偏 **±1.3 px**（x 方向偏 2.7px 就掉到 0.5 以下）。后果是**一次「位置对、框偏」
的检出被同时记成一笔 FN 和一笔 FP**。

同一批预测换官方口径（val 77 张、conf 0.25）：

| 类 | 四角差≤20px | IoU≥0.5 | 倍数 |
|---|---|---|---|
| `r` | 0.930 | 0.746 | 1.2× |
| `c` | 0.983 | 0.864 | 1.1× |
| `l` | 1.000 | 0.906 | 1.1× |
| `gnd` | 0.907 | 0.747 | 1.2× |
| `v` | 0.881 | 0.664 | 1.3× |
| `box` | 0.947 | 0.947 | 1.0× |
| `d` | 0.968 | 0.871 | 1.1× |
| `net_input` | 0.455 | 0.227 | 2.0× |
| `testpoint` | **0.000** | **0.000** | — |

`fn_fp.py` 现在有 `--crit {corner,iou}`，**默认 `corner`**（`--corner-tol 20`），
旧口径仍可用 `--crit iou` 复现历史数字。

### 4. 两条真窟窿（不是判据问题）

- **`testpoint` 召回 0.000**：YOLO 在 val 的 94 个 GT 上一个都不出。这正是
  `CV_PARTS = {"testpoint": cv_testpoint}` 存在的理由（阶段一合并后召回到 0.767）。
- **`net_input` 召回 0.455**：44 个 GT 漏 24 个，且 82% 是纯真漏检。全类最差。

### 5. 一条运维教训（写给未来的我）

一次后台任务连跑 imgsz 1024/1600/1920 三档 × 220 张 × `--workers 8`，
8 路并发各持一份 YOLO11m+torch 灌同一块 RTX 4080，1920 档算力约为 1024 的 3.5 倍，
**而且那一档根本不需要**（前两档已经给出答案）。用户报「电脑差点死机」。
**规矩：扫描一次最多两档、`--workers` 不超过 4、不再开 1920 这种档。**
