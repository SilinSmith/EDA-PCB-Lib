## 2. 关键判据：怎么判「没给位号」

**踩过的坑**：`assemble.py` 在位号读成功时会**直接拿位号当 key**，所以 `Name == key` 对
`"C5"`（正确）和 `"p004"`（兜底）**同时成立**。第一版用 `text_of(p) == p["id"]` 去判，
把 **1574 条本来就对的**也计进了错例，数字虚高到 8311。

**正确判据是 key 的「形状」**：兜底 key 形如 `^p\d{3,4}$`（小写 `p` + 3~4 位数字，
见 `eda-pcb\stage2\assemble.py:137` 的 `"p%03d" % i`），真位号一律大写字母开头。

## 3. 按「能不能修」重新切分（这才是决策依据）

判 `∅NNN` 的正则必须是 **`^\u2205\d+$`（`^\u2205` 是 U+2205 直径符号）**。
用 `r'^.\d+$'` 会把 `C15`/`R17` 一并吃进去，得到虚高的「不可修」数（这一版修正过）。

| 类别 | 条数 | 占比 | 可修？ |
|---|---|---|---|
| 文字对 | 1574 | 17.0% | — |
| 类型错 | 20 | 0.2% | 可修（量小） |
| 没给位号 · GT 名是 `∅NNN` | **3501** | 37.9% | **不可能**（图上没有） |
| 没给位号 · GT 名可读 | **2711** | 29.3% | **可修 ← 最大的一块** |
| 读错 · GT 名是 `∅NNN` | 513 | 5.6% | **不可能** |
| 读错 · GT 名可读 | **920** | 10.0% | **可修** |
| **配对合计** | **9239** | 100% | |

⇒ 不可修 **4014（43.4%）**、可修 **3631（39.3%）**。

## 5. 官方评分口径（决定了哪些字段真的算分）

`eda-pcb\schematic_parser\metrics.py`：

```python
# line 12 / 29
100 * (0.30*ComponentF1 + 0.25*PinF1 + 0.35*NetHypergraphF1 + 0.10*NetLineF1)
WEIGHTS = {'component': 0.30, 'pin': 0.25, 'net_hypergraph': 0.35, 'net_line': 0.10}
```

元件要对上，必须**同时**过四关（`metrics.py:224-252`）：

1. **key 完全相等**（`set(gc) | set(pc)` 按字典 key 配对）；
2. `type` 相等；
3. `bbox_ok`：默认 `bbox_mode='corners'`、`bbox_tol=20.0` ⇒ **四个角都相差 ≤ 20 px**
   （注意**不是** IoU，`metrics.py:129-146`）；
4. `component_text_ok`（`metrics.py:149-157`）：

```python
IC_TYPES    = frozenset({'box', 'ic', 'boxic'})               # data.py:33
VALUE_TYPES = frozenset({'r', 'resistor', 'c', 'capacitor'})  # data.py:35

ctype = gt.get('type')
if ctype in IC_TYPES:    return pred.get('Name')  == gt.get('Name')
if ctype in VALUE_TYPES: return pred.get('value') == gt.get('value')
return True          # ← 其余所有类型：文字一律算对
```

**三条由此推出的结论：**

* **只有 `box`/`ic`/`boxic` 比 `Name`，只有 `r`/`c` 比 `value`，其余类型的文字根本不参与评分。**
  所以 `gnd`/`v`/`testpoint`/`switch`/`led`/`net_*` 这些的**唯一门槛就是 key（=`Name`）+ type + 四角 ≤20px**；
  而它们中 `gnd`/`v`/`net_*` 的 GT key 恰好是 `∅NNN` ⇒ **这些类型在现有 GT 下几乎不可能拿到 TP**。
* **`gnd` + `v` 占了 `∅NNN` 的 3338/4144 = 80.5%**，而我们的 `stage1` 明明检出了 `gnd 2253 / v 1110`
  ——**检得出、名字不可能对**，于是每一个都同时吃一个 fp 和一个 fn。
* **`box` 类型要两样同时对**：GT 的 key 是**位号**（`U1`）、`Name` 是**型号**（`RP2350B`），
  而 `component_text_ok` 比的是 `Name`（型号）。我们现在的 `0001` 输出是
  `"U4": {"Name": "M0/OIM"}`（key 对了、型号读错）或 `"p004": {"Name": "p004"}`
  （key 与型号全错）。
  GT 全量抽样（前 60 张）里 `key == Name` 有 1618 个、`key != Name` 有 136 个，
  差值几乎全是 `box`（`U1→MSP432E401YTPDT`、`D1→1N4007`）。

### 5.1 当前分数构成（stage3_best 7.0634）

|---|---|---|---|
| component | 0.30 | 0.0853 | 2.56 |
| pin | 0.25 | 0.0073 | 0.18 |
| net_hypergraph | 0.35 | 0.1218 | 4.26 |
| net_line | 0.10 | 0.0059 | 0.06 |
| **合计** | | | **7.06** |

**注意**：`net_hypergraph` 与 `pin` 的键都是 `(元件 key, 引脚号)`，
所以上面这个 key 问题**同时把 0.35 + 0.25 = 0.60 的分一起锁住了**。

### 5.2 修好「可修的 3631 个」能拿多少（粗估）

若把 3631 个已经在框上配准、GT 名可读的元件全部正确命名，则
`tp 825 → ≈4456`、`fp 8734 → ≈5100`、`fn 8784 → ≈5150`，
component F1 ≈ 8912 / (8912+5100+5150) ≈ **0.465**（现 0.0853），

（真实收益会更小，因为按框 IoU 配准不等于「四角 ≤ 20 px」；但量级如此。）

## 6. 可行动的下一步（按性价比排序）

1. **位号挂载（2711 个没挂上）**：`c 796 / box 619 / r 569` 三项占 1984。
   这些框已经和我们检出的元件重叠，只是 `designator` 槽位空着。
   最直接的改法：在 `eda-pcb\stage2\assign.py` 的候选里，把**离元件最近的同族文字框**
   无条件提升为候选（现在的管束太紧），并放宽 `assign` 的搜索半径。
2. **位号识别（920 个读错）**：`box 371 / r 235 / c 230`。
   注意 `box` 的这 371 条里，多数是 **key 对了、`Name`（型号）读错** ——
   修它要的是「型号文本读准」，不是位号。
3. **`assemble.py:133-152` 补 `value`**：GT 里 `∅NNN` 元件的可读信息全在 `value`
   （`GND` / `3.3V` / `1.1V`），我们现在对非 `VALUE_TYPES` **恒写 `null`**。
   （但按 §5，这些类型的 `value` 不参与评分，所以此项**优先级低**，除非 net_hypergraph 用到。）
4. **`type_mismatch` 只有 20 条**，不值得单独优化。
5. **不再投入「文字框切分/生长/二值化」**：`narrow` 只有 2 条，全量 A/B 两次净零甚至净负。
