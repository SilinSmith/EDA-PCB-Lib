## 一、`∅NNN` 的官方定义

赛题指南 PDF：`Y:\workspace\EDA\赛题资料\赛题六：AI驱动的PCB原理图自动解析（芯粒CAD和制造浙江省工程研究中心&比昂芯0803Rev1.pdf`
（抽好的正文在 `Y:\workspace\EDA\docs\problem_statement.txt`，557 行；下引行号都是这个 txt 的）

全文只有一处出现 `∅`，在 `:364`：

> 第二层key 建议采用`pin_` 格式，其中来自原始数据中的pinNumber 字段。
> **如果 pinNumber 为空、∅ 占位符或 OCR 噪声，则会自动编号为 `pin_1`、`pin_2`…**

也就是说 PDF 把 `∅` 明确当作**「空」的占位符**。

而元件键为什么会变成 `∅109` 这种，能从 `:325` 反推出来：

> b) 编号顺序按照 **`componentID`** 的自然排序确定，因此第一个出现的RUN 变为RUN_1，第二个变为RUN_2，以此类推。

`componentID` 是**原始 ParsedJson 里的对象编号**。有名件的键就是它的位号（`U1`/`C151`/`R164`），
没有位号的对象（电源符号、地符号、网络标签、安装孔、马达……）就退化成 `∅<componentID>`。

**`∅` 元件的类型分布正好印证这一点**（220 张，4144 个）：

| 有 `∅` 的类型 | 数量 | | 从不出现 `∅` 的类型 |
|---|---:|---|---|
| `gnd` | 2195 | | `r` `c` `l` `d` `led` `box` `pin` `testpoint` |
| `v` | 1143 | | `switch` `mosfet` `bjt` `crystal_*` `fuse` |
| `net_input` | 323 | | `amp_*` `net_output` 之外的带位号器件 |
| `net_short` / `net_output` / `other` | 163 / 72 / 66 | | |
| `m3螺丝` `battary` `buzzer` `block` `net_bidirection` `jumper` `motor` `esd` `dc` `transfomer` `ant` `circle_header` `opt` `seg` | 合计 224 | | |

**规律非常干净：凡是图上会印位号的类型，一个 `∅` 都没有；凡是图上不印位号的对象，全都只有 `∅` 键。**

## 三、数字能不能重建？—— 不能

试过的四条路，全部走死：

1. **它跟几何位置无关。** 早前量过：同一行 y 上 `∅` 的 x 顺序是乱的（438/508/299/577/716/159/368），
   几何乱序率 ≈ 0.5。
2. **它是「整篇文档对象流」的编号，不是「元件序号」。** 稳定可复现的两条结构
   （以 `10GT\1\1.json` 为例，22 个元件、208 是最大编号）：
   - `∅N` 的引脚键恒为 `pin_{N-2}`：`109→107`、`113→111`、`117→115`、`121→119`、`125→123`、`200→198`、`208→206`
     （只有 `∅202→pin_202` 例外）；
   - 相邻无名符号之间**步长恰好 4**（109/113/117/121/125），跳到大编号时中间夹着 13 个有名元件。
3. **它不是「元件+引脚+导线」的总数。** 拿 `comps+pins+edges` 与最大 `∅` 比，比值 1.03~1.56，不收敛：

   | case | comps | pins | edges | max `∅` | comps+pins+edges | 比值 |
   |---|---:|---:|---:|---:|---:|---:|
   | 1 | 22 | 60 | 102 | 208 | 184 | 1.13 |
   | 2 | 28 | 48 | 40 | 181 | 116 | 1.56 |
   | 3 | 26 | 45 | 47 | 122 | 118 | 1.03 |
   | 4 | 24 | 43 | 60 | 151 | 127 | 1.19 |
   | 5 | 26 | 49 | 57 | 194 | 132 | 1.47 |
   | 6 | 38 | 68 | 86 | 242 | 192 | 1.26 |
   | 10 | 29 | 57 | 83 | 182 | 169 | 1.08 |

   ⇒ 计数器还覆盖了**输出 JSON 里根本没有的对象**（网络标签文字、junction、被过滤掉的图元……）。
4. **JSON 文件里的键顺序不是源文档顺序。** 220 个 case 里「按文件出现顺序编号单调」的有 **0 个**；
   而且同一张图的两个独立发布批次（`10gt.zip` 与 `10GT-0930.zip`）里键顺序完全不同
   （A 批 `U1, ∅109, ∅113, …`，B 批 `∅202, C151, C152, …`），但**键集和编号完全一致**。

**所以 `∅NNN` 是「确定性但不可从 PNG 重建」的。** 两个独立发布批次用同一套编号，
说明它不是一个随手生成的随机号；但它来自源文件的 `componentID`，图上没有任何地方印着它。

## 四、那它扣掉多少分？—— 比想象中少，真正的窟窿在别处

220 张 GT 共 **9609** 个元件，其中 `∅` **4214**（43.9%），**带真位号的 5395 个**。

- 我们目前最好成绩 `work\stage2_v9`：`component F1 = 0.1426`，`tp = 971`。
- `∅` 一个都匹配不上 ⇒ 最少 **4214 个 `fn`** 是白送的。
- **ComponentF1 的天花板** = `2×5395 / (2×5395 + 0 + 4214) = 10790/15004 =` **0.719**。
- 而我们只有 **0.1426**，`971 / 5395 =` **18.0%** 的真位号召回。

**⇒ 结论：`∅` 把 ComponentF1 的上限压在 0.719，但我们离上限还差 0.576 —— 瓶颈是我们自己的位号识别/挂载（18% 召回），不是 `∅`。**
把 ComponentF1 从 0.1426 推到 0.719，在总分里值 `0.30×0.576×100 ≈ +17.3 分`（我们现在才 15.48）。

## 五、顺手查出来两件必须记住的事

### 5.1 官方 GT 是**左下角坐标系**，我们已经在用（已核实）

PDF `:298` 与 `:501` 两处明说：

> `bbox [x1,y1,x2,y2]` … 使用**左下角坐标系**。x1<x2，y1<y2
> c) 坐标系沿用原始 **ParsedJson 的左下角坐标系**：x 轴向右增大，**y 轴向上增大**。

验证方法：把 `10_GTcase\0025-Altium Designer` 的 GT 框分别按「左上角」和「左下角（y→H−y）」画到原图上，并排对比。
**左下角那一版严丝合缝地落在 R4/R5/R6/R7、K1..K4、SW1、GND 符号上；左上角那一版全飘在空白处。**
证据图：`Y:\workspace\EDA\work\preview\_coord_0025_both.png`（左=左上角，右=左下角）。

我们的管线**不需要改**：`eda-pcb\stage2\assemble.py` 的 `stamp_pins()` 用的就是 `H - p[1]` 把图像坐标翻成 json 坐标，
`metrics.py` 也是在同一套坐标里比对 GT，所以本地 15.48 这个分数是自洽且可提交的。
