# 第十轮：黑白引脚与任意编号顺序修复

2026-10-11。对比起点为提交 `0ab91c80bfff323a3d256a3d45e07d55d6bd5269`，本轮沿用 `codex/improve-pin-network-parsing` 分支。只评估芯片引脚的所属元件、编号、名称；坐标仅供物理行配对，不计坐标与网络分数。

## 改变了什么

1. 删除按编号大小递增/递减筛掉候选的规则及数值阶梯重排。原理图符号常按功能排列，`17,48,55,58,80,114,10` 是合法序列。仍按文字与引脚的空间顺序整排匹配。
2. 为黑白图增加可靠证据入口。它要求实测框边、当前引脚点、连续的接框笔画及相应测量记录；单独的 `trusted` 标签、文字形似横线、陈旧点或明显位于框内的点不能获得资格。保留不确定候选原来的处理。
3. 名称从框内同侧同行取，编号从框外、实测横线上方取。沿原图黑色字形生成独立裁片，不擦除黑色笔画，不用邻脚号猜数字。字形在裁片边缘仍有8邻域连通延续时暂缓，避免截掉斜体笔画。
4. 可选 PP-OCR 直接读原灰度字形，固定加2和4像素白边，两次文字一致且各自置信度至少0.90才允许定向覆盖旧观测。两白边不是两个独立模型，仍可能一致读错。PP与CRNN的置信度不直接比较来选择同脚新旧读数。
5. 可靠框内名称不再被提前当作器件型号拿走。重复编号选择完整且实际可输出的候选，所选引脚保留自己的点和网络；不合并不同物理脚的坐标或网络。
6. 恢复缺失名称前，检查最终可用的旧编号框。只有明确跨框、多物理行、实测导线侵入或字形确被旧框截断时，才要求同脚完整新编号。新OCR低信、分歧或未生成裁片本身不能证明旧编号错误。确认新编号必须以真实绑定结果为准，并按 `min_conf` 过滤旧读数副本。只有实际赢得绑定的独立新编号才能解除旧名称对重复编号的冻结证据。

颜色门槛的原意是避免文字、边框、导线产生假引脚；此前只有颜色路径能满足新裁片入口，导致黑白图全部绕过这些改进。本轮增加与颜色接点并列的实测框边证据，不把可靠性检查整体删除。

## 名称库的取舍

本轮没有按编辑距离强制替换名称。`INP/INN`、`OUTP/OUTN`、`VDD1/VDD2`、`GND1/GND2`、`VS/VSS` 都可能同时合法，近似不能决定哪个正确。`type_list.md` 规定元件类别，未提供封闭的引脚名称枚举；Dataset300还有错标，不能直接当可信词典。

后续可用名称库提出候选、触发重读，或在器件型号和编号都有独立证据时交叉核验。最终采信仍需原图字形。大小写、反相横线及重复NC也需保留来源，不能用常见名称覆盖它们。

## 使用与验证

```powershell
python -m pip install -r requirements.pin-name-ocr.txt
$env:STAGE2_MONO_PIN_OCR = "on"
python -m stage2.run --stage1 <stage1目录> --out <输出目录> --texts both --device cpu
```

`STAGE2_MONO_PIN_OCR` 默认继承 `STAGE2_PIN_NAME_OCR`，支持auto/on/off。auto在可选依赖不可用时警告并回退；on在有合格裁片而模型不可用时失败；off零加载。不做OCR、未选相应角色或未达到min_conf时不强行追加读数。

新黑白路径只支持左右横向引脚。上下竖向、号码在导线下方、框边未测到、相邻字形无法分离的图仍走原流程。新增边界保护不能保证扫描数字永不误读。

本轮在安装PP和未安装PP的两个环境各通过432项单元及接入测试，覆盖裁片8邻域完整性、细数字1保留、非递增编号、陈旧/不确定证据、角色开关、阈值、缺依赖回退、伙伴编号与重复赢家自己的坐标/网络。正常CLI重新识别图1的最终JSON与冻结初始OCR的对照结果一致。10GT输出网络引用均可解析，未出现悬空成员；未据此宣称网络识别分数提高。

机器可读对照与逐脚错误见 [第十轮实测JSON](metrics/black-pin-fields-20261011.json)。
