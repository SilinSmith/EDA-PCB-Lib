# 第九轮：引脚编号错读修复

在第八轮提交 `4685555` 上修复编号识别。当前10GT彩图2–10的110个芯片引脚，编号正确从99增至110，最终元件键、编号、名称全部正确的输出从96增至108。修复11个错误编号后，还释放了图7被错误重复号占用的FB输出。原正确编号、名称及完整输出均未退化。

这是**固定stage1和初始OCR的本地开发集验证**。10GT已经参与开发，不能解释为隐藏测试或线上成绩；纯黑图1本轮不变，也不能用110/110保证新画风准确率。全10图本地严格均分50.2993→51.0430，整条PR仍低于颜色端点改动前的更早严格基线54.8662。

## 为什么会错

- 完整干净的6、9已经存在，旧CRNN仍把6读成o/8、9读成8/S。原数字框的自动扩边还会采入导线和框边，污染读数反而更自信，压过干净低置信数字。简单扩大白边、二值化、横向缩放及换角色条件不能稳定修复主要错误。
- 图6两个竖排GND/2被引脚间中分界切掉1像素笔画，又包含彩色接点旁的独立黑残渣。旧完整性检查正确发现风险，拒绝重读，所以最终缺号。只降低识别门槛不能恢复缺失字形。
- 图8 NC/6的旧框还包含绿色NC叉，彩色污染约72.27%，错读25。干净6的旧数字读数不足采信，补名保护一直暂缓NC，避免输出NC/25。
- 图7 FB/8本身读数正确；EN/6错读8后占用最终键，FB被淘汰。只改变重复号赢家无法同时恢复两个真实引脚。

## 实现

新增 `stage2/pin_number_crops.py` 与 `stage2/pin_number_reading.py`。流程为旧颜色/文字/引脚行读取→新数字复核→已有PP名称读取→归属和装配。新数字先于名称，是为了合法编号确认后释放NC的补名保护。

1. 只读取当前可信颜色接点、实际框边及框外数字走廊。新数字框与旧名称/数字路径分开；源图、旧候选和文档不变。
2. 仅在实测彩色接点附近、存在较大数字主体时，清除小型独立黑残留。竖排裁片最多扩展1个切向像素，只恢复已经被原框命中的连通笔画；遇到邻脚竞争、继续跨界或未知邻字仍拒识。保留旧框、旧完整性问题和每个删点/补全证据。
3. 数字直接使用完整原灰度字形，让PP执行自己的48像素归一化。**不经过名称路径的CRNN灰度32像素重采样。** 上一轮32→48数字对照较差，不能据此否定原字形直接读取，也不能把两条路径混称相同输入。
4. 固定2、4像素合成白边分别读取，两次必须输出相同的合法1–999数字，且各自置信度≥0.90并满足用户`min_conf`。不从多个变体挑最高置信结果，不按图号、GT或编号顺序补号。
5. 与已绑定编号相同则保留旧绑定，不因更高置信度重排重复号。需要改变时，若同完整字形的旧CRNN给出另一个≥0.90的合法数，则保留旧路径。该保护可能保留高置信错误，代价见后文。
6. 竖排方向来自当前同脚名称或同侧名称方向共识。缺少方向且6/9存在歧义时保持暂缓，不按编号递增方向猜测。
7. 合格新数字只优先匹配自己的当前实测接点。归属器再次检查目标新鲜性、实际框外位置、引脚行和跨行风险；不同模型的置信度不直接比较。没有证明的新结果保留旧读数。

沿用上一轮已校验版本、模型SHA的本地PP识别模型，新增`read_glyph`接口记录原裁片及真正送入ONNX session的张量SHA。原`read_normalized`名称接口保持不变。不开检测/方向分类器，不运行时下载，不修改原CRNN权重或GT。

## 开发之外的数字裁片及保护代价

沿用第八轮助手视觉复核的67个Dataset300数字裁片，10个来源/候选同源组，`human_verified=false`。使用原注释裁片和审核方向，只评价识别器，不证明自动定位/方向或完整JSON正确。旧模型没有训练图片清单，历史训练重叠未知。

先在10GT冻结原字形PP、2/4白边一致且≥0.90的策略，再看这67条：原CRNN45/67，新一致采信否则回退51/67，恢复7项、退化1项。PP两次把0060/T_217的4读成3，置信度均超过0.97，证明双视图高置信也不能保证正确。

**看过这个结果后新增通用CRNN强读数保护，再复用该67条诊断**：仍51/67，恢复6项、退化0项。它保护了原CRNN正确的4，同时抑制0123/T_82真实28的恢复，因为CRNN错读2但置信度0.998。这是受评测反馈影响后的保护设计，不能称最终策略的独立未见验证；仍需要新的审核数据评估泛化收益。
