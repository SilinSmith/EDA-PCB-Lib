# 第八轮：引脚名称识别器与独立裁片验证

在第七轮提交 `85b364f` 上增加可选的 PP-OCRv4 名称识别。彩图 2–10 的 110 个芯片引脚中，名称正确从 86 增至 107，最终完整正确项从 77 增至 96。编号正确仍为 99；原正确项未退化，重复编号的接点选择和全部网络引用保持稳定。

**这是固定上游输入的本地开发集回归，不能等同赛方线上成绩。** 全部 10 图严格均分从 49.2863 增至 50.2993；整条 PR 仍低于颜色端点改动前的更早基线 54.8662。本轮保留实际红绿交界端点，没有为贴合旧 GT 坐标回退固定外推位置。

## 为什么这次改善识别器

独立裁片诊断表明，24 个错名中有部分来自截字、邻行残字和框线，但 18 个在完整原灰度字形上仍读错。全量切换原灰度裁片会恢复 6 项、损坏 11 个旧正确项，名称反而降至 81/110。因此继续扩大裁框或一律擦线不能解决主因。

原 CRNN 权重的字符表不含英文括号，无法准确输出 `ADJ(GND)`、`VOUT(TAB)`；`FB→F/FE`、`PP→P` 等也发生在完整输入上。无词典 beam 解码、固定补白都有旧正确退化，本轮未采用。改用已存在的识别模型做对照，没有重新训练或修改原权重。

同样的 110 个完整名称裁片，CRNN 单角色精确识别 81/110，PP-OCRv4 为 107/110。该裁片指标与最终归属指标不同：旧归属器会在多个 OCR 角色间借读，不能只比较裁片就宣称输出正确。PP 对数字的对照只有 39/110，低于旧 CRNN 的 75/110，所以数字路径保持原方案。

## 实现与保护

1. 只处理有当前可信颜色端点和实际芯片框边的名称区域。保留四边文字走廊、原图字形完整性和旋转方向检查；失效方向、跨框和跨多条可信引脚行的观测不能获得优先权。
2. 两模型比较及新生产路径都使用相同的隔离后 32 像素灰度输入，旋转只作用于该裁片，并加 3 像素白边。PP 再执行其必需的 48 像素归一化。记录共享灰度与真正送入 ONNX session 的 float32 张量形状及 SHA，二者不会混称。
3. 只添加 `pin_name` 读数。新模型置信度达到固定 0.90 和用户 `min_conf` 后，仍须通过目标、框内和同脚走廊核验。不足则沿用旧读数；不按名称词典、图号、GT、编号顺序补字符或改变大小写。
4. PP 的字符概率算术均值与 CRNN 的几何均值不可直接比较。合格新名称只优先匹配自己的引脚；旧候选不能先挡住它再被置零。文字边中点实验开启时也必须遵守这个硬约束，实验仍默认关闭。
5. 编号冲突选择使用原 CRNN 名称证据的存在性及置信度，新名称的真实置信度保留供诊断，不用于重排重复号赢家。否则仅改名称就可能把另一个错号接点及其网络选进输出。已修复的第一版退化为图 8 GNDIO/8 被 MOTION/8 替代、图 10 VIN/1 切换到另一错号行；最终版均恢复原接点。
6. 补名不能激活污染旧号码。必须有当前同脚、合法且至少 0.55 并满足 `min_conf` 的数字观测确认实际绑定，否则暂缓新名称。图 8 NC/6 仍暂缓，避免新增 NC/25。

新文件为 `stage2/pin_name_ocr.py`、`stage2/pin_name_reading.py`；接入 `run.py`，补充 `assign.py`、`structmatch.py` 和 `assemble.py` 的匹配/编号竞争保护。最终比赛 JSON 不增加这些诊断字段，仍为左下角原点像素坐标；内部处理为左上角原点像素坐标。

## 开发之外的文字裁片对照

从 Dataset300 选 10 个来源/候选同源组，排除前 50 例和已知 10GT 近重复/型号线索。160 条候选经助手视觉复核后接受 142 条（75 名称、67 编号），拒收 18 条，纠正 11 条原标注；原图片和 JSON 不改。标签明确为助手复核，`human_verified=false`，不是人类仲裁真值。

75 个名称使用同样原标注裁片、已核实方向、隔离白边与共享 32 像素输入。方向由视觉审核给出，部分框仍带有线或符号，所以只评价识别器，不能称自动定位、方向判断或完整 JSON 的准确率。

| 方法 | 名称精确正确 |
|---|---:|
| 原 CRNN | 30/75（40.00%） |
| PP 直接读数 | 52/75（69.33%） |
| 已在开发集冻结的 ≥0.90 采信，否则保留 CRNN | 46/75（61.33%） |

固定门槛恢复 17 个旧错误，新增 1 个旧正确退化：`0074/T_127` 的 `DN→[DN`，PP 把左侧黑框线当成括号，置信度 0.91085。没有据此改门槛或删括号。高置信度仍会混淆 I/1、O/0 或漏字符，不能保证所有名称准确。

这些图片未用于本轮规则开发，但旧 CRNN 没有训练图片清单，无法排除曾参与历史训练；感知哈希与文本相似筛选也不能证明全部重绘同源图都已排除，因此不称严格模型未见测试。两模型对 75 裁片前向总计约 0.743 秒 / 1.101 秒，不是完整程序速度。

## 验证、运行与剩余问题

331 项全套测试在原环境和可选 OCR 环境均通过。110 个名称裁片的适配器与原 PP 调用实际输入、文本、置信度全部一致。全部 10 图真实 `stage2.run.process` 关闭/开启与受控回放和 pinindex 相同；图 6/8 共 12 个角色、`min_conf`、noOCR 组合检查通过。290 个网络引脚引用有效，全部重复编号的输出索引赢家不变，纯黑图 1 的 JSON 相同。

原环境实际缺少新依赖：`off` 不加载，`auto` 警告并退回旧结果，显式 `on` 抛 `PinNameOCRError`；图 8 完整入口及选项已验证回退。另用真实初始 OCR 跑通一次图 8 命令行，输出结构和 25 个网络引用有效，该次只作入口验证，不用于上述分数比较。

CPU 4 线程、固定初始 OCR 的一次测量：新增名称处理 10 图共 5.824 秒，中位 0.585 秒/图；真实受控入口关闭/开启合计 9.383 / 14.785 秒。包含几何准备、归属和文件写入，也受缓存与顺序影响，不作全流程耗时承诺。

新依赖安装到运行主程序的同一个 Python 环境：

```powershell
python -m pip install -r requirements.pin-name-ocr.txt
$env:STAGE2_PIN_NAME_OCR = "on"
```

然后照常运行主程序。默认 `auto` 有依赖时启用，否则保持旧结果；`off` 关闭。新识别器只加载 `rapidocr-onnxruntime==1.4.4` 包内 recognition 模型，实测 `onnxruntime==1.31.0`；校验模型 SHA `48fc40f24f6d2a207a2b1091d3437eb3cc3eb6b676dc3ef9c37384005483683b`。不加载检测/方向分类模型，不运行时联网下载。没有改原 CRNN 权重。

仍有 14 个最终完整项未正确：10 行名称已对但号码错/缺、2 行名称错、1 行 NC 配对未确认，另 1 行 FB 被重复错误编号淘汰。名称单项仅剩图 8 `U1.pin_6 NC` 暂缓、图 10 `U1.pin_7 VS` 保留旧 `VSS`（PP 读 VS 但置信度 0.7136 未达门槛）、图 10 `U2.pin_3 VIn` 读为 `Vin`。编号和重复号已是下一轮主要瓶颈，不能仅靠补名解决。
