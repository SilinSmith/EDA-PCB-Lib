# 第七轮：独立引脚裁片与 OCR 输入修正

相对提交 `ddb94e83d1d2a50cb6e97cd23975216917a2ce92`，指定 10GT 的彩图 2–10 中，110 个芯片引脚的完整正确输出 **75→77**，原正确项退化 **0**。名称单项 **84→86**，号码单项 **97→99**。第 1 张纯黑图的最终 JSON 完全相同。

本轮解决的是裁片漏出、字形截断、混框和彩色符号干扰这一类问题。方法由当前引脚几何和实际墨迹驱动，没有按图片编号、GT 字符串或编号序列补答案；收益有限，尚未解决全部 OCR 错字。

## 通用机制与采信条件

1. **从引脚建立区域。** 只有当前可信颜色端点及实际本体框接点才开放新路径。四侧的名称在框内、号码在框外独立生成，以同侧邻引脚限制归属。旧 OCR 不再是生成号码裁片的前提，因此原来漏框或混框也有机会补读。
2. **检查完整字形。** 号码触顶时依据真实墨迹补齐，但不越过上一可信引脚行。上下引脚的竖字可以偏在引脚轴线的一侧；仅补齐与已有字形相连、仍在本引脚归属区域内的笔画。遇到越界连接或归属未知的碎片时标记未解决，不拿截断裁片替换原结果。横向名称的完整性补齐还未全面覆盖。
3. **隔离符号与留白。** 彩色导线、引脚与附近颜色边缘使用已有颜色掩膜清理。数字只清理宽高不超过 2px、面积不超过 4 的孤立小块，保留断开的数字 1 和所有多位数字主体。原图不改；完整字形旋转后另加白色护边，留白不会把原图邻字或符号重新采进来。
4. **稳定识别输入。** 新裁片逐片进入原 CRNN，同一裁片不会因同批中出现更长文字而改变双向上下文。保存原灰度和轻清理的实际读数及输入哈希；没有彩色字形污染的名称优先保留原灰度，避免清理改变黑字边缘。没有按最高置信度或常见名称表择答案。
5. **有问题才补读，名称与号码分别采信。** 检查实际胜出旧框的缺失、截字、跨框、多行、颜色污染和重复号码；废弃脏框不用于推翻完整的旧读数。旋转号码借用可信文字方向，无方向的 6/9 歧义拒绝。旋转新号码替换不同旧号码仍需至少 0.85 置信度。
6. **保护名号配对及运行选项。** 新名称不能使污染旧号码变成新增最终引脚。号码未得到可用新观测确认时暂缓名称，并保存原因；没有新号码裁片时也直接检查旧号码像素。用户 `min_conf` 在内部判断和最终过滤中一致；关闭 OCR 或禁用对应 OCR 角色时不调用该角色的新读取。既有归属器仍可能把纯数字位号用于号码，`roles` 不是禁止最终 JSON 出现号码的选项。

图 6 的 OUT 保留原正确结果。图 8 的另一 NC 引脚，旧污染读数绑定为号码 25；补裁后名称能读回 NC，但真实数字 6 仍被模型读错、未达到采信门槛。因此暂缓该新名称，保留诊断，不新增错误的 NC/25。

没有实现黑色 NC 叉、黑色框线与黑字同色时的通用精确擦除。10GT 已参与开发，纯黑图、新画风、不完整框、复杂混色、完整检测及 VLM/融合后的收益尚未证明。下一步更有价值的是针对完整小字号裁片改善识别器，并在独立检查过的图片上验证，不能靠继续扩大裁框保证正确。
