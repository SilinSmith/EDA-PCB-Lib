## 1. 评分公式与权重（P5–P7）

```
Score_Accuracy_SingleCase = 100 × (0.30·ComponentF1 + 0.25·PinF1 + 0.35·NetHypergraphF1 + 0.10·NetLineF1)
Score_Accuracy           = (1/M) · Σ_{完成的案例} Score_Accuracy_SingleCase      # 分母是总案例数 M
FinalScore_Accuracy      = 0.95 × Score_Accuracy + 0.05 × (m/M) × Score_Token
FinalScore               = FinalScore_Accuracy + FinalScore_Data   # Data ≤ 10 分
```

- **Token 消耗是准确度分的 5%**，且是**排名分**（按消耗量分 K 个区间，最少消耗 = 100）。⇒ 少用 LLM token 直接换分。
- **未完成的案例会被双重惩罚**：分子少了它，`m/M` 又折一次 Token 项。
- 四项权重与我们 `eda-pcb\schematic_parser\metrics.py` 的 `WEIGHTS` **完全一致** ✓。
- 组件「文本正确」的口径与 PDF 一致：**IC 比 `Name`，电阻/电容比 `value`**。

## 3. 输出格式规范（附录一/二 + P7 + 附录四）

- 顶层 `{"components": {...}, "pins": {...}, "nets": {...}}`。
- `components.<key>`：`type` / **`Name`（首字母大写）** / `value`（可为 `null`，**要显式给**）/ `bbox`。
- **坐标系：沿用原始 ParsedJson 的左下角坐标系，x 向右增大、y 向上增大**；`bbox = [x1,y1,x2,y2]`，
  `(x1,y1)` 是**左下角**，`(x2,y2)` 是右上角（P11 L264-267）。
- 阈值：**bbox 20px**、**pin 坐标 5px**、**line 5px**（P7 L178/L190、附录四 #7）。
- `pins.<component>` → `pin_<pinNumber>`，每条含 `pinname` + `point {x,y}`。
  - 字母数字号写成 `pin_A5`；`"5,6,7,8,9"` 这种合并号要拆成 `pin_5..pin_9`。
  - pinNumber 为空 / 是 `∅` 占位符 / 是 OCR 噪声时，**自动编号为 `pin_1`、`pin_2`…**。
  - **Pin 匹配不是最近点匹配**（P18 L379：「评分时先要求 component key matched，再用 pin number 匹配」）
    ⇒ 号错的引脚不但丢自己，还可能被算成 fp（`pin_<错号>`）；**这解释了为什么 `extra` 是零、`missing` 很高**
    （我们宁可不发也不发错号，见 `stage2\assemble.py` 的 `BOX_PIN_NEED_NAME/DROP_UNREAD`）。
  - 引脚坐标 = **引脚 tip**（外侧框边缘、朝外的那一端）；附录三（P26 L503-508）写得更细：
    「每个元件均包含外侧框（outerbbox）和内侧框（bodybbox）：引脚 tip 点位于外侧框边缘，base 点连至内侧框」
    两种连接方式：① **绿色导线连红色引脚** ⇒ 取导线与引脚的交界点；② **引脚直接接引脚** ⇒ 两个 tip 重合。
    ⚠️ 我们 `_pinpos.py` 量到的超差引脚里 20~50 px 桶的误差中位数是 `dx +2.0, dy +29.0` ——
    **「发了 body 侧的 base 点而不是 tip」是待验证的假设之一**（另见 §3 的 5~10 px 桶 `dx −8.0`）。
- `nets.<netKey>`：`hyperGraph` + `edges`。
  - `hyperGraph` 写法 `(U1.A5,R1.1)`，**与 `pins` 的 `pin_` 键对齐**（附录四 #2/#3）。
  - **netKey 本身不要求和 GT 一致**，但 pinset 必须对（附录四 #4）——示例里就直接叫 `net_1`。
  - `edges` 是对象：`{"edge_1": [{x,y},{x,y}]}`，**每条线段两个点**；**线段数量要准确匹配**，多或少都扣分。
  - **线段必须放在正确 net 的 `edges` 下**，画错 net 不会因几何接近而得分（附录四 #5）。
- **重名元件**：转换器把同名元件统一编号 `_1,_2,_3…`（例：4 个 `RUN` → `RUN_1..RUN_4`，`GND` → `GND_4`）。
  ⚠️ 我们的 10GT 里同类元件（电源/网络标签）用的是 `∅NNN` 键 —— **两套命名并存**，而
  「Component key 非常重要，`U3` 写成 `U8` 会导致该 component、其 pins、相关 nets 都难得分」（附录四 #1）。
- **飞线（网络标签）**：同名（**VCC/GND 不算**）的网络标签/测试点跨图逻辑相连；`hyperGraph` 要含**全部逻辑相连的引脚**，
  包括各同名符号自己带的脚；**飞线 net 的 `edges` 是各连接点处的零长度线段**
  （例：`{"x":530,"y":630},{"x":530,"y":630}`）。
- 字符串**严格匹配**（`10k` / `10K` / `10K` 都是不同字符串，附录四 #6）。

## 6. 官方元器件库：当「整名/整号语料」没用（0），当「补号 / 改名」的两条规则值 **+2.46**（2026-10 结论修正）

体检工具（都在 `work\tools\diag\`，需从仓库根跑；库路径默认 `work\data\cpntLibrary.json`）：
`_libcov.py`（库对 GT 的覆盖率）、`_libopp.py`（库对我方交付产物的机会上界）、
`_pinlat.py`（IC 引脚排布的规则性）、`_pinpos.py`（引脚点距误差分解）、
`_pinmiss.py`（55 个缺失引脚的分桶）、`_libnum.py`（库当引脚号来源的上界）、
`_libsim.py`（**不改管线**，把库给的号/名直接写进交付 JSON 再打分 = 交付级收益）。

**① 库对 GT 的覆盖率**（官方 9 张 / 200 训练案例）：IC 名可命中率 **71.4%**（15 精确 + 6 未命中）/ **30.9%**
（248 精确 + 8 归一化 + 41 模糊；未命中里大量是 `U1`/`U2`/`RGB`/`Key` 这类**位号而不是型号**）；
命中库的 IC 上，GT 的 `pinname` 有 **99.0% / 64.9%** 出现在库记录里，`pinnumber` **100% / 54.8%**。
**r/c 的 `value` 命中率 0%**（值是 `100nF`/`10K`，库键里没有）⇒ 库对 value 通道**无任何帮助**。

**② 「拿库修我们已经输出的东西」的机会 ≈ 0**（`--pred work\_fnew`，双方都匹配上的 box/IC，120 个 GT 引脚）：
- 元件 `Name`：**17/17 已经全对**，库能带来的增分 **0**。
- 引脚号：`extra = 0` —— 我方**没有错号，只有缺号**（55 个），所以「拿库当号码词表纠错」的收益 **0**。
- 缺失脚的坐标**无法由库补出**：`_pinlat.py` 显示 IC 引脚列的间距非常规则（23 列，中位间距 **20.00 px**、
  间距最大偏差中位 1.00 px），但**号数→位置的顺序不单调**（相邻号在空间上相邻的只占 **35.7%**），
  用「号数轴上相邻已知脚线性插值」预测缺失脚坐标：**只有 1/17 落在 5 px 内**（52 个缺失脚里 27 个在号数轴两端、8 个号不是数字）。

**③ 真正的损失结构（2026-10 修正）** —— 55 个缺失引脚的成因分桶，**半径必须用 8 px**（引脚列间距 ~20 px，
30 px 会串到隔壁脚；半径 30 时出现的 `E-swap 13` 桶在 8 px 下**整桶消失**，是伪影）：
`A3` 名读到、桩在、**只缺号** **22**（40%）｜`C` 附近无名 **14**（25.5%）｜`A2` 名+号都读到但无桩 **9**（16.4%）｜
`A1` 名+号+桩都在却号读错 **7**（12.7%，实测这些引脚读到的号里**没有一个含 GT 号**）｜`D` 同位同名号不同 2。
⇒ 最大矛盾是「**号的召回**」（A3+A1+D = 31/55 = 56%），第二是检测（A2+C = 23/55 = 42%）；
不存在「号键撞车」（`extra 0` 也支持）。逐 case 缺脚数：1:5 · 2:10 · 3:2 · 4:6 · 5:12 · 7:5 · 8:9 · 9:1 · 10:5。

**④ ★ 库真正值钱的两条规则（`_libnum.py` 量上界、`_libsim.py` 量交付级收益）**
- 规则 A（**补号**）：某引脚**名读到了**（且绑在 GT 那个位置的桩上）但**号没读到** ⇒ 查 `库[型号].pins` 中
  名字与它相等的记录；若该名字在库里**唯一映射到一个号**，就用那个号做 `pin_<号>`。
- 规则 B（**改名**）：某引脚**号读到了**但名字读错 ⇒ 查库里该号对应的名字，**唯一时才改写**。
- 上界（`_libnum.py --radius 8`，55 个 missing）：库里同型号+同名能给出 GT 号的 **40**；其中
  「名字唯一映射一个号」的 **20 个，20/20 都是 GT 号 ⇒ 规则 A 的精度 100%**；规则 A 真正落得下去的那一块
  （名读到+桩在）**14 个里唯一且对 6**。库键来源：GT 名命中库 ×13、**我方预测名命中库 ×13**（用我们的 `Name` 查库不掉命中）。
- 交付级实测（`_libsim.py`，官方 9 张，基线 `work\_fnew` = **66.3024**，新口径）：
  | 模拟 | 补号 | 改名 | pin F1 | 总分 |
  |---|---|---|---|---|
  | 只规则 A（`--mode uniq`） | 6（6 对） | — | 0.4951→0.5353 | **67.3085**（+1.0061） |
  | 规则 A（`--mode pickfree`，多号时挑没用过的） | 10（9 对） | — | →0.5462 | **67.5797**（+1.2773） |
  | **规则 A + 规则 B** | 6（6 对） | 4（4 对） | 0.4951→**0.5936** | **68.7659（+2.4635）** |
  明细：`tp 44→54`、`fn 76→66`、**`fp 21→17`**（改名同时消掉 4 个假阳）、`pin.name_mismatch 7→3`；
  `net_hypergraph / net_line` 不变（补进去的引脚**不进任何 net**）。
- 实现要点：规则 A 需要「桩 + 绑定到该桩的引脚名」（stage2 `_assigned` 的 `raw_pins[j].name`；
  ⚠️ 名字读数框**不在引脚点上**，用框中心判「名读到」会得到 0/55），规则 B 需要「读到的号」；
  两条规则都**不需要 GT**，且必须**唯一映射**才动手（多号时精度掉到 90%）。
- 代价：交付包要带上 `work\data\cpntLibrary.json`（1.76 MB / 337 键），stage2 要能加载它。

## 7. 评测环境（2026-10，用户 m35611 转述）

| 项 | 值 | 对我们的含义 |
| --- | --- | --- |
| 操作系统 | **Ubuntu 24.04 LTS** | 交付链要能在 Linux 跑：路径分隔符、文件名大小写敏感、无 PowerShell、junction→符号链接；`submission\run.py` 必须纯 Python 且不依赖 Windows 专有件 |
| GPU | **NVIDIA A800-80GB × 8** | 显存不再是约束（本地 16 GB 卡的 WDDM 溢出问题不存在）；可以多卡/多进程并行跑 case、把 Stage2/CRNN 搬上 GPU、跑本地 VLM |
| 网络 | **允许**（可调用外部 LLM API，打榜练习阶段参赛队自费） | 不必只依赖注入的 `LLM_BASE_URL`；但要先弄清 `Score_Token` 到底统计谁（官方 API 的用量，还是自报）——这决定「本地 VLM」在 token 分上是赚还是无意义 |
| 算法自由度 | 用户原话：「你可以尽可能写针对GPU优化的算法」 | 高分辨率多尺度/切图检测、批量化推理、多卡切分都是允许的方向 |
