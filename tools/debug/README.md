# 单样例调试器（IDE debug 模式）

**一句话**：对任意一个 case 生成一张可交互的 HTML，把官方那 100 分**逐条摊开** ——
哪个元件被判错、错在哪一步、修好能涨多少分，并且能在图纸上直接看到那个框。

```powershell
cd Y:\workspace\EDA

# 一个 case
python work\tools\debug\dbg.py --case 0001

# 全部 220 张 + 总览页（按各项丢分排序，找最值得点进去看的图）
python work\tools\debug\dbg.py --all

# 换一版产物对比
python work\tools\debug\dbg.py --case 0001 ^
    --pred work\_submit_out220y\final_results ^
    --runs work\_submit_out220y\runs ^
    --log  work\_submit_out220y\decision_log.json ^
    --out  work\debug_y
```

产物：

| 文件 | 内容 |
|---|---|
| `work\debug\index.html` | **总览页**：220 张按「网络 / 引脚 / 元件 / 导线」四种口径分别排序，一眼看出哪几张最该看 |
| `work\debug\<case>.html` | **单图调试页**（单文件，图纸 base64 内嵌，约 0.6 MB，可直接发给别人） |
| `work\debug\_index.json` | 上面那份表的原始数据（方便脚本再筛） |

## 页面有哪五块

1. **「这 100 分是怎么没的」** —— 四个指标各一行：权重、tp/fp/fn、P/R/F1、得了几分、
   丢了几分。点开每一行，看这一类错误**具体是哪几条**，以及
   **「如果把这一类全修好，这个指标能涨多少」**。
   顶上的绿色框是**一句话诊断**：把四个指标的所有「修满收益」排个序，直接从最大的往下修。
2. **图纸叠加** —— 全部框和点画在原始图上。
   - **虚线 = GT 的框，实线 = 我们输出的框**；颜色 = 判决。
   - 滚轮缩放、拖动平移、「适应窗口」；**点下面表格的任意一行，图上会飞过去并高亮**。
   - 图层开关（GT 元件框 / 我们的元件框 / GT 引脚点 / 我们的引脚点）+ 判决筛选（只看漏检 / 误检 / …）。
   - 鼠标悬停任意框，直接弹出这一条的 GT 值、我们的值、类型、中心距和中文原因。
3. **管线步进** —— 阶段一 → 二 → 三 → VLM → 官方打分，每一步往里加/减了多少元件、网络、引脚。
4. **逐条对账** —— 元件 / 引脚 / 网络 / 导线四个表格，一行一条判决，带中文原因。
5. **环境** —— 这一页用的评测口径（容差、`unkeyed_match` 等）。

## 判决颜色（和官方 `metrics.py` 的计分口径一一对应）

| 颜色 | 判决 | 对分数的影响 |
|---|---|---|
| 绿 `正确` | 键 / 类型 / 外框 / 文字全过 | tp +1 |
| 蓝 `漏检` | GT 有，我们没有 | fn +1 |
| 红 `误检` | 我们有，GT 没有 | fp +1 |
| 橙 `文字不符` | **型号**（`box` 比 `Name`）或**参数值**（`r/c` 比 `value`）不一致 | **tp 不加，fp +1，fn +1（一笔亏三处）** |
| 紫 `外框不符` | `bbox_mode='corners'` 下 `max|Δ| > 20px` | 同上 |
| 黄 `类型不符` | 类型判定不一致 | 同上 |
| 橙 `引脚位置偏` / `引脚名不符` | 号对上了但点偏 > 5px / 名字不同 | 同上 |

> 官方口径是 `score = 100 × (0.30·元件F1 + 0.25·引脚F1 + 0.35·网络F1 + 0.10·导线F1)`，
> 是**加权 F1 之和**，不是正确率。每一项的 F1 都是**整张图**算的：
> 图上物品越多，错几个就越致命。

## 一个位置同时出现「漏检」和「误检」

这是最常见的误读。**FN/FP 是在键匹配之后统计的**：只要检测对了、类型对了、位置对了，
但**位号（键）没读对**，同一个位置就会同时记一次 FN（GT 侧）和一次 FP（预测侧）。
页面上会看到蓝、红两个框叠在一起 —— 那不是「检测错了」，是「键错了」。
`_keyfix.py` / `_misspair.py` 量的就是这一批。

## 自校验（重要）

`ledger.py` 是**照抄**官方 `schematic_parser/metrics.py` 的判定顺序重写的一份，
但它逐条留痕。生成时会同时调官方 `evaluate_case`，
**两边的总分和四个指标的 tp/fp/fn 必须完全一致**；不一致就在页面顶上打红条报警。
220 张全部逐张核对过（`dbg.py --all` 输出的 `官方 xx.xxx` 与左边那个数一一相等）。

## 三个文件

| 文件 | 干什么 |
|---|---|
| `ledger.py` | 镜像官方判定但逐条留痕：`build_ledger()` → 每一行一个判决 + 中文原因；`headroom()` → 每类错误修满能涨多少分 |
| `report.py` | 把 ledger 渲染成单文件可交互 HTML（CSS/JS 内嵌，无外部依赖） |
| `dbg.py` | CLI：找 GT / 找预测 / 找阶段产物 / 写文件 / 出总览页 |

## 踩过的坑

- `headroom()` 里读 `p["stats"]["buckets"]`，而 `ledger_lines()` 一开始没返回 `buckets` ⇒
  `KeyError: 'buckets'`。四个 ledger 函数的 stats 都要有 `buckets`。
- `report.render()` 不能同时用 f-string 和末尾 `% (...)` 格式化：CSS 里满是 `100%`、`%.2f%%`，
  会被 `%` 吃掉（`ValueError: unsupported format character '}'`）。**整个返回用字符串拼接。**
- **`missing` / `extra` 的 row 必须带上 `gt_bbox` / `pred_bbox`** —— 一开始只记了键，
  结果整颗没检测到的 IC 在图上没有框，最该看见的东西反而看不见。
- 引脚点图层默认要开：很多 case 的主要丢分就是引脚（权重 0.25），
  默认关掉就看不到「我们一个引脚点都没输出」。
