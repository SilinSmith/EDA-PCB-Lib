# 工作流编辑器（ComfyUI 式）

**为什么要它**：手里有 20 多份实测记录、十几个被否掉的方案、几十个处理步骤，
但它们散在 README、报告和我的记忆里。你想改流程只能靠嘴描述，我改代码也容易
把已证伪的路再走一遍。所以把流程画成一张**可编辑的节点图**：你在图上改，我照图改代码。

**当前图上是「目标架构」，不是「现在跑的管线」。** 目标架构长这样：

```
   证据层（互相不调用）            融合与仲裁（一个循环）
   ┌──────────────┐
   │ ①符号检测     │──┐
   │ ②文字区域定位 │──┤            ┌─────────┐   ┌──────────┐   ┌──────────┐
   │ ③CRNN 识别    │──┼──证据───▶ │ 证据池  │──▶│ 约束求解 │──▶│ 装配/导出 │
   │ ④VLM 读取     │──┤            └─────────┘   └────┬─────┘   └──────────┘
   │ ⑤导线与结点   │──┤                  ▲           │ 低置信项
   │ ⑥引脚点       │──┤                  │           ▼
   │ ⑦初始网络     │──┘            ┌──────────┐   ┌──────────┐
   └──────────────┘                │ 迭代控制 │◀──│ 定向重扫 │◀─┐
                                   └──────────┘   └──────────┘  │
                                                   ┌──────────┐ │
                        ★ 常识与先验表 ──约束─────▶│ 冲突与缺口 │─┘
                                                   └──────────┘
```

**一句话**：读取器只负责「我认为这是什么」，互相不覆盖；一个全局求解器
拿着**常识约束**把全部证据求成一个自洽的解；解不出来的项，**带着已确认的上下文**
回去定向重读，新证据回池，再解，最多 3 轮。

## 打开

直接双击（不需要服务器、不需要联网、零依赖）：

```
Y:\workspace\EDA\work\flow\workflow.html
```

它是从 `work\tools\flow\graph.json` + `template.html` 生成的**单文件**。
改完 `graph.json` 后重新生成：

```powershell
python work\tools\flow\build.py
```

`build.py` 会顺手做自检：**每条连线的两端必须指到真实存在的端口**，
悬空就报错并列出是哪一条（画不出来等于没连）。

## 怎么用

| 操作 | 怎么做 |
|---|---|
| 平移 / 缩放 | 空白处拖动 · 滚轮 |
| 移动节点 | 拖节点的标题栏 |
| **连线** | 从右侧的**小圆点**拖到另一个节点的**左侧小圆点**，松手即成 |
| 删除 | 点中节点或连线，按 `Delete` |
| 改内容 | 点中节点 → 右侧 inspector：标题/副标题/种类/分组/代码位置/说明/参数 k-v/端口列表 |
| 加节点 | 左栏「加节点」选种类；或「从已有候选节点里加」 |
| 适应窗口 / 整理布局 | 顶部按钮（整理布局会按分组重排成竖列） |
| **存盘** | 自动（浏览器 `localStorage`，键 `eda_flow_v1:<指纹>`），关掉页面再开还在 |

节点左边的色标就是它的种类：

| 色标 | 种类 | 意思 |
|---|---|---|
| 绿 `现在有` | `exec` | 现在代码里就有，改名/挪位置/调参即可 |
| 红 `★要新写` | `new` | **要新写的模块**，这是本轮要讨论的部分 |
| 黄 `标尺` | `param` | 只在旁边看，不参与执行 |
| 蓝 `数据` | `data` | 中间产物 |

## 怎么把改动交回给我

**方式一（推荐）**：点顶部 **「改动说明」** → 弹窗里是全 Markdown，
包含新增/删除的节点、新增/删除的连线、改过内容的节点、以及**画布上全部节点按分组 + 全部连线**。
点「复制」，直接贴回对话里。我拿到就能照着重写代码。

**方式二**：点 **「导出 JSON」** → 复制 → 存成文件（比如 `work\tools\flow\graph_v2.json`），
告诉我路径。我 `diff` 两份 JSON，落成代码改动。

**别点「还原基线」**——那会把你的改动丢掉。

## 为什么要有 `plausible`（合理性检查）—— 和 `conflict` 不是一回事

`conflict`（冲突与缺口）问的是：**两个来源说法不一致吗？** —— 「CRNN 说 `10nF`、VLM 说 `1uF`」。

`plausible` 问的是：**这个结果整体讲不讲得通？** —— 它要能发现**所有来源都一致地错**的情况。
最典型的就是用户举的例子：**VCC 和 GND 短接**。这时候每个读数单独看都没矛盾、
`conflict` 一条都报不出来，但整个电路是错的，必须去找错在哪一段。

| 层次 | 检查什么 | 例子 |
|---|---|---|
| **结构（`plausible`）** | 电气 / 拓扑 / 分布是否讲得通 | VCC 与 GND 短接｜同网络里电源和地共存｜去耦电容必须一端电源一端地｜GND 引脚必须落在接地网络上｜同排同类元件参数应同分布 |
| **内容（`fixstr`）** | 字符串本身像不像一个真东西 | `STC12O5A6OS2` → `STC12C5A60S2` |

**输出不是「改」，而是「可疑位置 + 支持证据 + 建议先扫哪」。** 因为分布类的信号（一排 `10nF` 里有一颗 `5uF`）
**可能是真设计**（电源滤波本来就常见 10uF 级），所以 `plausible` 只报可疑、**不自动改** ——
判断交 `llm_judge`，这才是用户说的「LLM 需要判断到底是因为电路图本身的性质，还是识别错了」。

强信号（VCC/GND 短接）可以直接触发整段重扫；弱信号（参数离群）必须先问。

`fixstr` 的边界：字符混淆表 `O↔0、I↔1↔l、S↔5、B↔8、Z↔2、G↔6、q↔9`，
依据 = 同图命名家族 + 已知型号表 + 混淆表，**必须可解释，没依据不许改**。
⚠️ 官方 Q&A Q9 说「电容 `uF`/`μF` 以图片为准」⇒ **绝不做单位归一化**。

## 为什么要有 `batch`（请求合并）

用户的账：**跑一次测试，模型要回复几万条请求。**

| 通道 | 现在 | 说明 |
|---|---:|---|
| 位号 | 4094 次 | 一格一次 |
| 引脚网格 | **1051 次** | **已经合并过**：4025 个引脚 → 8 格拼一张网格 |
| 值 | 3492 次 | 一格一次 |
| 型号 | 1021 次 | 一格一次 |
| **合计** | **9658 次 / 220 张 ≈ 44 次/张** | 预估可压到 **≈3350 次（−65%）** |

**引脚通道就是先例** —— 它本来就是 8 格拼一张网格问的，说明这条路走得通。

⚠️ **这是「请求数」的收益，不是「token 数」的收益**：总像素基本不变，
省的是每次请求的固定开销（提示词重复、连接开销）。所以别指望账单按比例降 —— 用户也说了
「如果这样没有带来额外的开销就算了」。

⚠️ **真正的风险**：拼图会让**每一格变小**，而值通道对裁片尺寸**极其敏感**
（`100nF` 的尾巴 `F` 被切掉时 margin 25 只有 0.212，margin 80 才 0.9423）。
所以 `batch` 的输出必须能被 `ev_vlm` 接受或拒绝，**每格精度掉超过 1 个百分点就不做**，先拿 30 张 A/B。

## LLM 在这张图里的三个位置

这是被问到的第一个问题，所以单独写一节。**LLM 没有消失，它从一个「末端总闸」变成了一个「循环里的参与者」。**

| 位置 | 节点 | 干什么 | 和现在的区别 |
|---|---|---|---|
| **① 证据源** | `ev_vlm` ④ LLM/VLM 读取 | 读位号 / 值 / 器件型号 / 逐引脚号名，结果作为**一条证据**进池 | 现在是**四条独立通道各自直接改文档**，谁也不能被质疑 |
| **② 仲裁者** | `llm_judge` ★ | 只对**求解器解不出来的那几条**，带着上下文（类型 + 已定位号 + 邻居读数 + 冲突内容）给判断或给重读计划 | 旧阶段三是**对全部槽位问一遍** → 8 张 A/B 里与 off **逐项完全相同**，却要 **161.7 s/张**，所以被停用 |
| **③ 读者** | `rescan` ★ | 按 `llm_judge` 给的计划，回到指定区域**带着上下文**重读 | 现在根本没有重扫；`desig_all`（无差别重读）实测是**负收益**（25.0823 < 25.0946） |

关键区别就是那句**「带着上下文问」**：
不是把同一块图再问一遍「这是什么」，而是告诉它「这是电容，位号 `C155` 已确定，缺 `value`，
它左边那颗读出来是 `10nF`，现在 VLM 说 `1uF`、CRNN 什么都没读出来，你判断一下」。

成本也可控：每张图通常只有几条解不出来的 ⇒ 远低于全量仲裁的 161.7 s/张。
预算对照：现管线 220 张 **4727 s（78.8 min）**，2 小时还有约 1.5 倍余量。

每个节点的 `说明`（点开 inspector 看）都写进了**实测数字**和**被否过的方案**——
这是为了防止把已经证伪的路再走一遍（例如 `desig_all` 判负、`STAGE2_GLOBAL_MATCH` −0.477、
导线 `weld` 桥接会掉 P、值外扩改小 −0.124）。

## 三个文件

| 文件 | 作用 |
|---|---|
| `graph.json` | **工作流的唯一真相**：节点、连线、分组、参数、说明 |
| `template.html` | 编辑器本体（占位符 `__GRAPH__`）。改交互逻辑改这里 |
| `build.py` | `graph.json` + `template.html` → `work\flow\workflow.html`，并自检连线 |
| `graph_v1_current.json` | 上一版：现在真实跑的管线（37 节点，做对照用） |

**为什么内嵌 JSON 而不是 `fetch`**：浏览器打开 `file://` 页面时 `fetch('graph.json')`
会被 CORS 挡掉，所以 JSON 必须写进 HTML。JSON 里的 `</` 要转义成 `<\/`。

## 踩过的坑

- **★ 一定要看这条**：编辑器会把你的改动自动存进浏览器 `localStorage`。最早用的存盘键是
  固定字符串 `eda_flow_v1`，结果我重新 `build.py` 之后，你刷新页面看到的**还是上一次存的旧图**
  （「你没更新 workflow.html 啊」就是这么来的）。现在存盘键里带了 `graph.json` 的**指纹**
  （`eda_flow_v1:<指纹>`），基线一改指纹就变、旧存盘自动失效；并且打开时会把所有旧指纹的存盘清掉。
  顶部那个 `v<指纹> · N 节点 / M 连线` 就是当前文件的身份证 —— **它变了就说明图换了**。
  如果还是觉得不对，按 `Ctrl+F5` 强制刷新，或点「还原基线」。
- `graph.json` 里数组最后一个元素**不能带尾逗号**，否则 `json.loads` 报
  `Expecting value: line N column 3`。
- 端口位置用 `el.offsetTop` 算（节点是 `position:absolute`，所以 `.port` 的 offsetParent 就是节点），
  不要用 `getBoundingClientRect`——那会被 `transform: scale()` 后的缩放值污染，连线会错位。
- 导出 JSON 走 `<script type="application/json">` 内嵌，不用 f-string 拼 HTML（`%` 和 `{` 都会打架）。
- 节点没有输入端口（如 `know`、`input`）或没有输出端口（如 `metrics`）都要能正常渲染，
  `.map()` 空数组返回空串即可，别加特判。
